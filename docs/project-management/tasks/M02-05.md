## 2. Phạm vi triển khai

### 2.1 Đăng nhập — `POST /api/v1/auth/admin/login` (FR-090, FR-091)

- Request `{ username, password }` (bắt buộc). Response `200`: `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn: 900, admin: { id, username, roles: [...] } }` (API_SPEC §11.7, OpenAPI `/auth/admin/login`).
- Sai tài khoản/mật khẩu → `401 INVALID_CREDENTIALS`, message chung, không lộ tài khoản có tồn tại hay không (FR-090). Tài khoản không tồn tại vẫn chạy verify Argon2id với dummy hash để tránh rò rỉ qua thời gian phản hồi (đề xuất — xem §12 D-13).
- Tài khoản `isActive = false` → `401 INVALID_CREDENTIALS` chung, không lộ lý do.
- Đăng nhập thành công: reset `failedLoginAttempts` về 0; tạo 1 row `AdminRefreshSession` (chỉ lưu hash refresh token, `expiresAt` theo TTL đã chốt).

### 2.2 Refresh — `POST /api/v1/auth/admin/refresh` (FR-090)

- Request `{ refreshToken }`. Response `200`: access token mới + refresh token mới (xoay vòng); refresh token cũ bị thu hồi (`revoked_at` set, không xóa row — row cũ là bằng chứng cho reuse detection).
- **Claims của refresh JWT (FIX-07):** `sub` = admin id, `sid` = id của row `AdminRefreshSession` (liên kết token với session trong DB), `type: "refresh"` (phân biệt loại token), `iat`, `exp` (TTL đã chốt). Access JWT có `type: "access"` tương ứng (bổ sung nhỏ so với API_SPEC §2.3 — chỉ thêm claim `type`, không đổi các claim đã chốt) **và `sid` = id của session đã cấp token (FIX-10 — xem §2.3: guard kiểm tra trạng thái session)**. Verify refresh: (1) chữ ký bằng `JWT_REFRESH_SECRET`; (2) `type` phải là `"refresh"` — access token đưa vào `/refresh` → `401 INVALID_REFRESH_TOKEN` (không bao giờ chấp nhận token chỉ vì chữ ký hợp lệ); (3) `sid` phải khớp row session còn hiệu lực; (4) SHA-256 của toàn bộ JWT trình lên phải khớp `token_hash` của row. Guard `/me`/`/logout` từ chối refresh token (kiểm tra `type: "access"`).
- **sid thay đổi sau mỗi lần refresh (FIX-10 — hành vi chủ ý):** `sid` trong access JWT là id của row `AdminRefreshSession` đã cấp token; rotation tạo row mới và đánh dấu row cũ `ROTATED` — nên access token cũ có thể **mất hiệu lực ngay khi refresh thành công**, không chờ tới logout hay hết hạn 15 phút. Đây là hành vi chủ ý (bảo mật chặt hơn: token gắn với đúng session đã cấp nó), không phải lỗi — brief ghi rõ để tránh hiểu nhầm rằng mọi access token vẫn sống tới khi logout. Test AC-07 kiểm tra access token cũ ngay sau refresh, trước logout.
- **Rotation nguyên tử (FIX-02):** trong một transaction duy nhất, conditional update `UPDATE admin_refresh_sessions SET revoked_at = now(), revoked_reason = 'ROTATED', replaced_by_session_id = $newSid WHERE id = $sid AND revoked_at IS NULL AND expires_at > now()` — chỉ request nào update được đúng 1 row mới được phát hành token mới. Request thua race xử lý theo Idempotency-Key D-14 (không dùng cửa sổ grace tự do — xem dưới). Không được chỉ dùng transaction thường rồi mặc định race đã giải quyết — phải có test đồng thời (AC-17).
- **Idempotency-Key cho refresh (D-14 — thay thế grace window, ChatGPT không duyệt grace nguyên trạng):** client gửi header `Idempotency-Key` (UUID, một key cho mỗi thao tác refresh; retry cùng thao tác dùng cùng key; thiếu header → `400 VALIDATION_ERROR`, details field `Idempotency-Key`). **Phối hợp đồng thời (FIX-11 + FIX-15):** mỗi cặp (refresh token, Idempotency-Key) có một operation record trong Redis, key = `auth:refresh:op:` + hex(SHA-256(UTF-8 của `tokenHashHex + "|" + idempotencyKey`)) — đầu vào nối bằng đúng một ký tự `|` (tokenHashHex dài cố định 64 ký tự hex nên không mơ hồ). Record là JSON: PENDING = `{"state":"PENDING","ownerId":"<uuid v4>","claimedAt":<epoch ms>}`; COMPLETED = `{"state":"COMPLETED","ownerId":"<uuid>","sid":"<id session mới>","ciphertext":"<base64(IV||ct||tag)>","createdAt":<epoch ms>}` (xem FIX-16). (1) Request đến thử claim operation nguyên tử: `SET opKey <PENDING envelope> NX EX 15` — `ownerId` là UUID v4 ngẫu nhiên riêng cho mỗi lần claim; chỉ request nào SET thành công là **leader**, được phép rotation; request khác là **follower**. (2) Follower poll opKey tối đa 5 giây (mỗi 50ms): thấy `COMPLETED` → giải mã response đã lưu (dùng `sid` metadata để dựng AAD) và trả lại (không rotation thêm, không revoke-all); sau 5 giây vẫn `PENDING` → `503 SERVICE_UNAVAILABLE` + `Retry-After` (không kết luận replay oan — thao tác đang thực sự chạy). (3) Leader kiểm tra quyền sở hữu ngay trước DB transaction (Lua `checkOwner`: đọc opKey, so ownerId — mất lease → bỏ DB, chuyển thành follower); rồi chạy DB transaction (conditional update + session mới + audit); thành công → ghi COMPLETED **chỉ qua Lua script kiểm tra đồng thời ownerId + state PENDING** (owner khớp + state PENDING → ghi đè, EX 10; owner không khớp hoặc state đã COMPLETED → không thay đổi record); thất bại (token không hợp lệ/hết hạn/đã thu hồi) → xóa claim **chỉ qua Lua script kiểm tra đồng thời ownerId + state PENDING** (owner khớp + state PENDING → DEL; không khớp hoặc state đã COMPLETED → không làm gì — không bao giờ xóa claim của leader khác và không bao giờ xóa trạng thái COMPLETED), rồi trả lỗi 401 tương ứng. **Mọi thay đổi trạng thái operation (gia hạn, chuyển COMPLETED, xóa) đều qua Lua compare-and-set kiểm tra đồng thời ownerId + state PENDING (FIX-20); không dùng DEL/SET thường lên opKey.** (4) **Leader mất lease giữa chừng (FIX-15 — fencing):** leader bị treo quá 15 giây, lease hết hạn, leader mới claim — leader cũ tỉnh lại **không được** xóa claim của leader mới (Lua owner check chặn), **không được** ghi COMPLETED (Lua owner check chặn), **không được** trả cặp token đã phát hành cho caller của nó dù đã commit DB (cặp token bị hủy; session mới đã tạo nhưng chưa từng được giao, sẽ bị revoke-all khi client retry theo AC-05) — leader cũ chuyển thành follower (poll tối đa 5 giây chờ COMPLETED của leader mới, không thấy → 503). Conditional update DB vẫn là lớp bảo vệ cuối cùng: chỉ một rotation được commit cho mỗi token (row chỉ chuyển ACTIVE→ROTATED một lần; leader thứ hai tới DB sau sẽ thấy row đã ROTATED → chuyển thành follower, không tạo session thứ hai). (5) **Leader chết giữa DB commit và ghi Redis (FIX-11):** PENDING hết hạn sau 15 giây; retry sau đó đánh giá lại theo DB — token đã `ROTATED` → replay theo AC-05 (revoke-all, đăng nhập lại). Đây là **đánh đổi availability đã được ChatGPT chấp nhận có điều kiện (27/11/2026 ~14:33)** — không phải bảo đảm retry luôn idempotent: session mới có thể đã được tạo nhưng response chưa được giao; **không** mô tả cửa sổ lỗi là luôn chỉ vài mili-giây — process có thể chết hoặc bị treo lâu hơn. **Không** lưu response mã hóa trong DB để phục hồi (tránh mở rộng dữ liệu nhạy cảm trong DB). (6) **Redis lỗi khi claim/đọc/ghi cache (FIX-13 + FIX-17):** refresh yêu cầu Redis để phối hợp idempotency — Redis lỗi → `503 SERVICE_UNAVAILABLE`, không rotation khi không phối hợp được (không fallback bộ nhớ, vì claim bộ nhớ chỉ đúng trong một instance). Không bao giờ fallback sang chấp nhận refresh token đã bị thu hồi. **Không suy luận cache miss = thao tác chưa từng chạy** — trạng thái thu hồi luôn đọc từ DB row, cache không bao giờ thay thế DB.
- **Fencing ở tầng DB (FIX-18):** Redis lease + PostgreSQL commit là hai hệ thống riêng, không có transaction chung — **không có cách nào đóng hoàn toàn cửa sổ TOCTOU giữa checkOwner và DB commit** nếu chỉ kiểm tra Redis trước transaction. Brief **không gọi** cơ chế hiện tại là "fencing DB hoàn chỉnh". **Failure mode đã định nghĩa — "lease-lost commit":** leader kiểm tra owner thành công, bị treo ngay sau đó, lease 15 giây hết hạn, leader B claim; leader cũ tỉnh lại và chạy DB transaction — conditional update vẫn thành công (DB chỉ kiểm tra row còn ACTIVE, không kiểm tra quyền sở hữu operation) → commit một session không bao giờ được giao. Hậu quả: đúng một session được tạo (không trùng lặp — conditional update vẫn bảo đảm chỉ một rotation commit), cặp token bị hủy theo quy tắc fencing (post-commit Lua complete chặn vì owner không khớp), leader cũ thành follower → 503; client retry sau PENDING hết hạn → AC-05 revoke-all → đăng nhập lại. Đây là cùng một lớp kết quả với trường hợp leader chết sau DB commit đã được ChatGPT chấp nhận có điều kiện (trade-off availability) — không rò rỉ token, không tạo session trùng, không kết luận replay oan cho một thao tác khác. Xác suất: cần process treo > 15 giây đúng trong cửa sổ check→commit (bình thường ~1 mili-giây, giữa hai round-trip kề nhau không có công việc xen giữa). Giảm thiểu: checkOwner đặt sát ngay trước conditional update (không có bước nào xen giữa); kiểm tra lại owner ngay sau commit trước khi giao response; row lock của PostgreSQL trên session row đã serialize các conditional update cạnh tranh (không cần advisory lock riêng — lock row đã đủ). **Phương án thay thế nếu ChatGPT muốn fencing DB thật (chưa đề xuất chính thức):** bảng operation trong DB (`auth_refresh_operations`: token_hash + idempotency_key unique, owner_id, state PENDING/COMPLETED, expires_at) — claim + rotation + chuyển COMPLETED cùng một DB transaction (UPDATE operation row với điều kiện owner_id + state PENDING trong cùng transaction với rotation; 0 row → abort cả rotation) — fencing thật vì rotation và kiểm tra quyền sở hữu commit/rollback cùng nhau; response mã hóa vẫn chỉ lưu trong Redis (giữ nguyên lựa chọn không lưu response trong DB); đổi lại cần migration mới ngoài D-15 (quyết định D-16 — migration thuộc thẩm quyền Henry) + bỏ cơ chế claim Redis. **Đề xuất của Revision 06: chấp nhận failure mode "lease-lost commit" như trên (không gọi là fencing DB hoàn chỉnh) — nhờ ChatGPT chọn giữa phương án này và bảng operation trong DB.**
- **Ghi Redis không xác định kết quả (FIX-19):** phân biệt hai loại lỗi khi ghi COMPLETED: (a) **chắc chắn chưa thực thi** — lỗi kết nối xảy ra trước khi lệnh được gửi (pool lỗi, connect thất bại) → lệnh không chạy, record vẫn PENDING; (b) **mơ hồ** — timeout/mất kết nối sau khi lệnh đã gửi → Redis có thể đã ghi COMPLETED nhưng client không nhận được xác nhận. Quy tắc: leader **không được suy luận trạng thái cache từ việc mất kết nối** — sau lỗi mơ hồ, leader phải đọc lại record (GET opKey) để xác định trạng thái thực: thấy COMPLETED (owner của mình) → ghi đã thành công, trả response cho caller; thấy PENDING (owner của mình) → ghi chưa chạy, trả response + release qua Lua owner+PENDING (chỉ khẳng định đã xóa khi Lua trả về đã xóa — lỗi/mơ hồ khi xóa → không khẳng định, TTL 15 giây là backstop dọn claim); thấy record vắng mặt hoặc owner khác → lease đã mất, áp dụng fencing (hủy cặp token, follower poll → 503); đọc lại cũng lỗi (Redis vẫn down) → leader trả response cho caller của nó (cặp token đã commit trong DB, thuộc đúng thao tác này — giao cho caller là đúng) và **không khẳng định gì về trạng thái cache**; retry sau sẽ đọc trạng thái thực (Redis hồi → COMPLETED → response; record vắng + DB ROTATED → AC-05). Lua xóa chỉ xóa khi ownerId khớp **và** state vẫn PENDING — không bao giờ xóa COMPLETED (FIX-20). Giữ nguyên fail-closed: không fallback bộ nhớ, không coi cache miss là bằng chứng thao tác chưa chạy.
- **Mã hóa response cache (FIX-13 + FIX-16):** AES-256-GCM. Encryption key `REFRESH_IDEMPOTENCY_ENCRYPTION_KEY` trong config là **base64 của đúng 32 byte ngẫu nhiên** (44 ký tự base64 có padding) — `validateAuthEnv` giải mã base64 và từ chối nếu không đúng 32 byte (không chấp nhận chuỗi 32 ký tự thường — AES-256 cần key 32 byte, không phải 32 ký tự). IV 12 byte ngẫu nhiên cho mỗi lần mã hóa, không bao giờ tái dùng dưới cùng một key. **Cache envelope (FIX-16):** COMPLETED lưu dưới dạng JSON `{"state":"COMPLETED","ownerId":"...","sid":"<id session mới>","ciphertext":"<base64(IV 12 byte || ciphertext || auth tag 16 byte)>","createdAt":...}` — `sid` mới lưu **ngoài ciphertext** dưới dạng metadata (sid chỉ là id session, không phải secret), để follower dựng AAD trước khi giải mã. AAD (authenticated additional data) = UTF-8 của `sid + "|" + tokenHashHex + "|" + idempotencyKey` — ràng buộc ciphertext với đúng session mới, đúng token hash và đúng operation key; AAD được AES-GCM xác thực — metadata `sid` bị thay đổi → AAD sai → giải mã thất bại. Cache sai định dạng, sai AAD hoặc auth tag không hợp lệ → `503 SERVICE_UNAVAILABLE` (lỗi server — không fallback sang xử lý refresh như request mới). DB là nguồn đúng duy nhất cho trạng thái thu hồi; Redis chỉ là nguồn trả response của thao tác trong TTL — cache miss + row còn ACTIVE → đánh giá như thao tác mới; cache miss + row đã ROTATED → replay AC-05.
- **Sau khi cache hết TTL (FIX-12):** cùng token + cùng key sau TTL → không còn response idempotency; token đã `ROTATED` → xử lý replay theo AC-05 (revoke-all), **không** tạo session mới, **không** xử lý như request mới. (Sửa kỳ vọng sai trong Revision 03: "retry sau TTL xử lý như request mới".)
- **Ma trận lỗi Redis sau claim (FIX-17):** Redis lỗi khi claim → 503, không rotation; Redis lỗi khi follower poll → 503, không kết luận replay; leader ghi COMPLETED lỗi kết nối Redis → phân biệt lỗi chắc chắn chưa thực thi với lỗi mơ hồ và đọc lại trạng thái thực trước khi kết luận (xem FIX-19); caller hiện tại vẫn nhận response khi cặp token đã commit trong DB; leader không khẳng định đã xóa claim hay cache vẫn PENDING khi không xác minh được — TTL 15 giây là backstop dọn claim; Redis restart làm mất PENDING trong lúc leader chạy → leader kiểm tra owner thất bại → chuyển thành follower (poll tối đa 5 giây, không thấy COMPLETED → 503); Redis restart làm mất COMPLETED trong TTL → retry → cache miss + DB ROTATED → AC-05; leader hết lease nhưng vẫn chạy → fencing (mất quyền ghi COMPLETED/trả response, xem FIX-11); follower hết 5 giây poll → 503 + Retry-After; leader thất bại trước DB commit → xóa PENDING chỉ qua Lua owner check. Chi tiết đầy đủ xem §7.
- **Lý do thu hồi session (FIX-09):** mỗi lần thu hồi row `admin_refresh_sessions` phải ghi rõ `revoked_reason` (enum mới `RefreshSessionRevocationReason`: `ROTATED` | `LOGOUT` | `LOGOUT_ALL` | `ADMIN_REVOKED` | `REUSE_DETECTED`) + `replaced_by_session_id` (nullable, id của session mới khi rotation). Chỉ có `revoked_at` thì không phân biệt được rotation với logout — backend sẽ hoặc báo oan đánh cắp token, hoặc bỏ lọt replay. Quy tắc: `ROTATED` → kiểm tra replay (AC-05); các lý do còn lại → `401 INVALID_REFRESH_TOKEN` (AC-06); `REUSE_DETECTED` → `401 TOKEN_REUSE_DETECTED` (AC-06 — xem FIX-14). **Ràng buộc dữ liệu (FIX-09, thuộc định nghĩa migration D-15 đã được Henry duyệt):** session còn hiệu lực ⇔ `revoked_at IS NULL AND revoked_reason IS NULL`; session đã thu hồi ⇔ cả hai đều có giá trị — CHECK `(revoked_at IS NULL) = (revoked_reason IS NULL)`; `replaced_by_session_id` chỉ được đặt khi lý do là `ROTATED` — CHECK `(replaced_by_session_id IS NULL OR revoked_reason = 'ROTATED')`; `replaced_by_session_id` có FK tự tham chiếu tới `admin_refresh_sessions(id)` ON DELETE SET NULL. **Quy tắc reason khi revoke-all (FIX-14):** session đang ACTIVE → `REUSE_DETECTED`; session đã thu hồi trước đó (LOGOUT/ADMIN_REVOKED/...) → **giữ nguyên reason cũ** (không phá lịch sử); row của token bị replay giữ `ROTATED` (nó là bằng chứng truy vết nguồn phát hiện replay; `replaced_by_session_id` đã trỏ tới session phát hành từ nó). Cần **migration bổ sung riêng trong M02-05** (không sửa migration M02-01 đã nghiệm thu) — xem D-15 (Henry đã duyệt 27/11/2026 ~14:19).
- **Phân biệt replay với hết hạn/thu hồi khác (FIX-01 + FIX-09):** trình lại token của row có `revoked_reason = ROTATED` → AC-05 (`401 TOKEN_REUSE_DETECTED` + revoke-all). Token hết hạn, hoặc row có `revoked_reason` khác (`LOGOUT`, `LOGOUT_ALL`, `ADMIN_REVOKED`) → `401 INVALID_REFRESH_TOKEN` (đăng nhập lại, AC-06). Row có `revoked_reason = REUSE_DETECTED` → từ chối, không dùng tiếp. Không tạo session mới khi refresh thất bại.

### 2.3 Logout — `POST /api/v1/auth/admin/logout` (FR-090)

- Header `Authorization: Bearer <access_token>` + body `{ refreshToken? }`. Response `204`.
- **Phạm vi logout (FIX-06):** logout **có gửi** `refreshToken` → thu hồi đúng session đó (refresh row revoked + access token blacklist) — logout một phiên. Logout **không gửi** `refreshToken` → thu hồi **toàn bộ session** của tài khoản (mọi row `admin_refresh_sessions` revoked) + blacklist access token — logout toàn bộ tài khoản (đề xuất; khác với cách đọc chữ §11.7 "refresh token (nếu gửi)" — vì nếu không gửi mà chỉ thu hồi access thì refresh session còn sống sẽ cấp access mới ngay, logout mất tác dụng; cần ChatGPT duyệt điểm này). Frontend logout chuẩn luôn gửi `refreshToken`; trường hợp không gửi (refresh đã mất/hết hạn) vẫn logout toàn bộ cho an toàn.
- **Thứ tự kiểm tra blacklist (FIX-03):** guard xác minh chữ ký + thời hạn JWT trước; **sau đó kiểm tra blacklist Redis trước khi chấp nhận request**; token trong blacklist → `401 UNAUTHENTICATED`. Redis lỗi khi kiểm tra blacklist → **fail-closed**: từ chối request bằng `503 SERVICE_UNAVAILABLE` + `Retry-After` (Error Catalog §11) — không được bỏ qua blacklist rồi chấp nhận token đã logout (AC-18).
- **Kiểm tra trạng thái session (FIX-10):** guard, sau khi verify chữ ký + thời hạn + blacklist, còn kiểm tra row session theo `sid` trong access JWT: session phải tồn tại, chưa revoked, chưa hết hạn — session đã revoked (bất kỳ lý do nào) → `401 UNAUTHENTICATED`. Nhờ đó logout một session vô hiệu hóa **mọi access token thuộc session đó** (kể cả access token cấp trước lần refresh gần nhất), không chỉ access token hiện tại. Access token không có `sid` (token cấp trước M02-05 — không tồn tại trong thực tế vì chưa có admin nào đăng nhập) → từ chối. Access token cũ hết hiệu lực ngay khi refresh thành công (sid trỏ tới session đã ROTATED) — hành vi chủ ý, xem §2.2.
- **Cập nhật API_SPEC/OpenAPI (FIX-06):** API_SPEC §11.7 + OpenAPI phải ghi rõ ngữ nghĩa logout khi thiếu `refreshToken` (thu hồi toàn bộ session) — hiện spec chỉ ghi "refresh token (nếu gửi)". Xem §13.
- Thu hồi access token: lưu hash SHA-256 của access token vào Redis với TTL = thời gian còn lại tới `exp` (xem §12 D-06).
- Sau logout, access token cũ → `401 UNAUTHENTICATED`; refresh token cũ → `401 INVALID_REFRESH_TOKEN`.

### 2.4 Thông tin tài khoản — `GET /api/v1/auth/admin/me` (FR-081)

- Header `Authorization`. Response `200`: `{ id, username, roles: [{ id, name }], permissions: ["products.view", ...] }` — danh sách permission đã gộp vai trò + ngoại lệ từng tài khoản, deny (`granted = false`) thắng allow (API_SECURITY §2, `UserPermission`).
- Phân quyền resolve trực tiếp từ DB tại thời điểm request (cùng logic union mà middleware M02-06 sẽ tái dùng) — **không cần middleware RBAC trong M02-05** (xem §12 D-10).
- Thiếu token → `401 UNAUTHENTICATED`; access token hết hạn → `401 TOKEN_EXPIRED`.

### 2.5 Khóa tài khoản — FR-091 (ngưỡng do M02-05 chốt, chờ ChatGPT duyệt — §12 D-01)

- Sai liên tiếp tới ngưỡng → `423 ACCOUNT_LOCKED` + `retryAfter` (giây). Tài khoản đang bị khóa → `423` (kể cả khi mật khẩu đúng — theo FR-091 "báo rõ"; đánh đổi với FR-090 đã ghi ở §12 D-01).
- Mở khóa tự động sau thời gian khóa; Super Admin mở tay (API_SECURITY §1 — cơ chế mở tay thuộc M06-01/admin users, không thuộc M02-05).
- Trạng thái khóa dùng đúng 2 cột schema đã có: `users.failed_login_attempts` (CHECK ≥ 0) + `users.locked_until`.

### 2.6 Rate limit — tái dùng `RateLimitService` (M02-02)

- Login: `adminLoginIp` 5 lần/phút/IP + `adminLoginAccount` 10 lần/phút/tài khoản (fail-closed; Redis lỗi → fallback bộ nhớ tạm trong tiến trình, theo quyết định đã chốt ở M02-02 FIX-04).
- `GET /me` + `POST /logout` (đã đăng nhập): `adminAuthed` 300 lần/phút/tài khoản (fail-open theo rule hiện có).
- Refresh: chưa có kind riêng — đề xuất ở §12 D-05 (fail-closed vì refresh token tương đương credential).
- Vượt giới hạn → `429 RATE_LIMITED` + header `Retry-After` (Error Catalog §9).
- **Giới hạn của fallback bộ nhớ (FIX-04):** counter bộ nhớ chỉ dùng chung trong **một** backend instance, không chia sẻ giữa nhiều instance — không tuyên bố fallback bảo đảm rate limit toàn hệ thống; khi chạy đa instance, Redis là nguồn đúng duy nhất. AC-09/AC-10 kiểm tra đúng giới hạn này.

### 2.7 Cấu hình và secret

- Validate fail-fast lúc boot (theo mẫu `validateRedisEnv`/`validateMeilisearchEnv` trong `ConfigModule.forRoot`): `JWT_SECRET` và `JWT_REFRESH_SECRET` tối thiểu 32 ký tự ngẫu nhiên (API_SECURITY §1), `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` đúng định dạng thời gian; thiếu/sai → boot lỗi với message rõ ràng, không dùng secret mặc định trong code.
- `.env.example` (repo root) **đã có sẵn** 4 biến `JWT_SECRET`, `JWT_REFRESH_SECRET`, `JWT_EXPIRES_IN=15m`, `JWT_REFRESH_EXPIRES_IN=7d` (placeholder — TTL refresh 7d chưa phải quyết định đã chốt, xem §12 D-02). M02-05 chỉ xác minh + ghi tài liệu, không commit secret thật.
- Quy trình xoay JWT secret: API_SECURITY giao "M02 chốt" — đề xuất ở §12 D-11 (runbook, không code tự động xoay secret).
- **Tách biệt hai secret (FIX-05):** `JWT_SECRET` chỉ ký/xác minh access token; `JWT_REFRESH_SECRET` chỉ ký/xác minh refresh token; hai giá trị không được trùng nhau (config validation từ chối nếu trùng). Chi tiết thời gian chấp nhận secret cũ + xử lý session cũ khi xoay — xem §12 D-11.
- **Encryption key cho cache idempotency (D-14):** `REFRESH_IDEMPOTENCY_ENCRYPTION_KEY` (base64 của đúng 32 byte ngẫu nhiên, khác `JWT_SECRET` và `JWT_REFRESH_SECRET`; validate trong `validateAuthEnv` — giải mã base64, từ chối nếu không đúng 32 byte); dùng AES-256-GCM mã hóa response refresh lưu tạm trong Redis (TTL 10 giây). Không có key này → fail-fast khi khởi động.

### 2.8 Ánh xạ lỗi

- Mọi lỗi auth theo đúng Error Catalog: `UNAUTHENTICATED` / `INVALID_CREDENTIALS` / `TOKEN_EXPIRED` / `INVALID_REFRESH_TOKEN` / `TOKEN_REUSE_DETECTED` (401), `FORBIDDEN` (403, chỉ dùng khi có permission check — không thuộc M02-05), `ACCOUNT_LOCKED` + `retryAfter` (423), `RATE_LIMITED` + `Retry-After` (429). ## 3. Quy tắc kỹ thuật bắt buộc

- **Truyền token chỉ qua header `Authorization: Bearer`** (API_SECURITY §1): không nhận token qua query string, **không nhận token qua cookie cho API** (cookie chỉ dùng cho cart token). Response trả token trong JSON body theo API_SPEC §11.7 — mâu thuẫn với dòng "HttpOnly cookie" ở backlog M02-05, xem §12 D-04.
- **Refresh token chỉ lưu hash** (`admin_refresh_sessions.token_hash`, unique) — không lưu plaintext; không ghi token/mật khẩu/refresh token plaintext vào log (API_SPEC §12 "Không log").
- **Mật khẩu chỉ verify bằng Argon2id** với encoded hash ở `users.password_hash` (NFR-006); không trả hash trong bất kỳ response nào; không giới hạn độ dài tối đa thấp (tối thiểu 8 ký tự — API_SECURITY §1; chính sách cụ thể xem §12 D-07).
- **Không sửa schema/migration M02-01 đã nghiệm thu** nếu chưa chứng minh có thiếu sót và được ChatGPT duyệt (lệnh giao M02-05). Schema hiện tại đã đủ: `User` (passwordHash, isActive, failedLoginAttempts, lockedUntil), `AdminRefreshSession` (tokenHash unique, expiresAt, revokedAt), `Role`/`Permission`/`RolePermission`/`UserRole`/`UserPermission`, `AuditLog`.
- **Rotation nguyên tử:** conditional update trên session cũ trong transaction (FIX-02); không rotation trùng lặp khi refresh đồng thời.
- **Blacklist fail-closed:** guard kiểm tra blacklist sau khi verify JWT, trước khi chấp nhận request; Redis lỗi → `503 SERVICE_UNAVAILABLE`, không chấp nhận token đã logout (FIX-03).
- **Phân biệt loại token:** mọi verify đều kiểm tra claim `type` (`access`/`refresh`); không chấp nhận token sai loại dù chữ ký hợp lệ (FIX-07).
- **Audit trong cùng transaction:** audit lockout/reuse/revoke-all ghi trong cùng transaction nghiệp vụ với thao tác khóa/thu hồi (FIX-08); audit không chứa token/mật khẩu/hash.
- **Mỗi lần thu hồi session phải ghi rõ lý do:** `revoked_reason` (FIX-09) + `replaced_by_session_id` khi rotation; không suy luận lý do từ `revoked_at`.
- **Access JWT mang `sid`; guard kiểm tra trạng thái session:** session revoked/hết hạn → `401 UNAUTHENTICATED` (FIX-10).
- **Refresh yêu cầu `Idempotency-Key`:** thiếu header → `400 VALIDATION_ERROR`; cùng token + cùng key → trả response đã lưu; cùng token + key khác → replay (D-14).
- **Phối hợp Idempotency-Key (FIX-11 + FIX-15 + FIX-18):** claim operation nguyên tử PENDING/COMPLETED trong Redis với ownerId ngẫu nhiên riêng; mọi thay đổi trạng thái qua Lua compare-and-set kiểm tra đồng thời ownerId + state PENDING (FIX-20); leader mất lease bị fencing (không ghi COMPLETED, không trả response, không xóa claim của leader khác); **"lease-lost commit" là failure mode đã định nghĩa (leader mất lease sau checkOwner nhưng commit DB thành công → cặp token bị hủy, 503, retry → AC-05) — không gọi là fencing DB hoàn chỉnh**; follower chờ tối đa 5 giây rồi 503, không kết luận replay oan; leader chết giữa DB và Redis → retry sau PENDING hết hạn xử lý theo AC-05.
- **Hết TTL cache (FIX-12):** cùng token + cùng key sau TTL → replay AC-05, không tạo session mới.
- **Mã hóa cache (FIX-13 + FIX-16):** key base64 đúng 32 byte; IV 12 byte ngẫu nhiên; AAD ràng buộc sid + tokenHash + key; envelope JSON với sid metadata ngoài ciphertext; cache hỏng/sai AAD/tag → 503; Redis lỗi → 503, không fallback chấp nhận token đã thu hồi.
- **Ma trận lỗi Redis (FIX-17 + FIX-19):** mọi lỗi Redis khi claim/poll/ghi → 503 fail-closed; restart mất PENDING/COMPLETED → fallback theo DB (AC-05 khi đã ROTATED); xóa PENDING chỉ qua Lua owner check + state PENDING; **ghi Redis mơ hồ → đọc lại trạng thái thực trước khi kết luận, không khẳng định trạng thái cache khi không xác minh được**.
- **Reason khi revoke-all (FIX-14):** ACTIVE → REUSE_DETECTED; đã thu hồi trước đó giữ nguyên reason; row bị replay giữ ROTATED; trình token REUSE_DETECTED → 401 TOKEN_REUSE_DETECTED.
- **Không làm middleware RBAC của M02-06.** M02-05 chỉ cần JWT AuthGuard (xác thực đã đăng nhập) cho `/me` và `/logout` — không kiểm tra permission (API_SPEC §10.5: 2 endpoint này yêu cầu `*` = đã đăng nhập bất kỳ).
- **Không tạo tài khoản admin mẫu hoặc secret giả** (bootstrap Super Admin là M06-01). Test tạo user trực tiếp bằng Prisma trong setup test với Argon2id hash thật — không có endpoint/seed tạo user trong code sản phẩm.
- **Không merge.** Không làm auth khách hàng (FR-093/FR-094, P1) và không làm M02-04 (chờ D-06).

- **Idempotency (D-14/AC-17):** e2e 2 request refresh đồng thời cùng token + cùng key → request thứ hai chờ rồi nhận cùng response, đúng 1 session mới, không replay oan; cùng token + key khác → replay + revoke-all; thiếu header → 400; cache response hết TTL 10 giây → trình lại token cũ (cùng key hay khác key) → replay AC-05, **không** tạo session mới (FIX-12 — sửa kỳ vọng sai của Revision 03).
- **Lỗi process tại 3 thời điểm (FIX-11/FIX-15/FIX-17):** test leader chết (giả lập bằng mock/fault injection) — (a) trước DB commit → retry cùng key đánh giá lại từ đầu (rotation chạy bình thường); (b) sau DB commit nhưng trước khi ghi Redis COMPLETED → retry trong lúc PENDING còn hạn → 503 (không replay oan); retry sau PENDING hết hạn (15 giây) → replay AC-05 + revoke-all (cặp token đã phát hành bị mất, client đăng nhập lại); (c) sau khi cache COMPLETED → retry nhận đúng response đã lưu. **Fencing (FIX-15):** test leader bị treo quá 15 giây → leader mới claim (ownerId khác) → leader cũ tỉnh lại DEL → claim của leader mới còn nguyên (Lua owner check); leader cũ mất lease sau DB commit → không ghi được COMPLETED, không trả response cho caller, chuyển follower poll → 503; hai leader cùng tới DB → chỉ một rotation commit (conditional update), leader thứ hai thành follower.
- **Redis mất cache/restart + ma trận lỗi (FIX-13/FIX-17):** e2e dừng/xóa Redis test giữa chừng → refresh token đã ROTATED không được cấp token mới (fail-closed 503 khi không đọc được cache phối hợp; DB vẫn là nguồn đúng cho trạng thái thu hồi); refresh token còn ACTIVE + cache trống → rotation chạy bình thường (đánh giá mới). Test từng lỗi Redis: claim lỗi → 503 không rotation; follower poll lỗi → 503 không kết luận replay; leader ghi COMPLETED lỗi kết nối → caller hiện tại vẫn nhận response, retry sau → AC-05; restart mất PENDING trong lúc leader chạy → leader chuyển follower → 503; restart mất COMPLETED trong TTL → retry → AC-05.
- **Cache envelope (FIX-16):** e2e sửa `sid` metadata trong COMPLETED envelope → follower giải mã thất bại (AAD sai) → 503; envelope sai định dạng JSON/thiếu field → 503; auth tag bị sửa → 503; không trường hợp nào xử lý refresh như request mới.
- **Lease-lost commit (FIX-18):** e2e giả lập leader treo > 15 giây giữa checkOwner và DB commit (fault injection: dừng process sau checkOwner, để lease hết hạn, leader khác claim, rồi cho leader cũ chạy tiếp) → assert: conditional update của leader cũ vẫn commit (1 session mới duy nhất), Lua complete bị chặn (owner không khớp), cặp token không được giao cho caller, leader cũ thành follower → 503; retry sau PENDING hết hạn → AC-05 revoke-all; assert không có session thứ hai và không có token nào rò rỉ ra ngoài.
- **Ghi Redis mơ hồ (FIX-19):** e2e giả lập (a) ghi COMPLETED timeout sau khi Redis đã ghi → leader đọc lại thấy COMPLETED → trả response đúng; (b) lỗi kết nối chắc chắn chưa thực thi → leader trả response + release qua Lua owner+PENDING (assert Lua trả về đã xóa); (c) đọc lại cũng lỗi → leader trả response, không khẳng định trạng thái cache; (d) Lua release khi state đã COMPLETED → no-op, record COMPLETED còn nguyên; (e) Lua complete/release với owner sai → no-op.
- **Lua CAS owner + state (FIX-20):** unit test cho 3 Lua script (extend/complete/release) với ma trận owner đúng/sai × state PENDING/COMPLETED → chỉ đúng owner + PENDING mới thay đổi record; các trường hợp còn lại no-op.
- **Access token cũ sau refresh (FIX-10/AC-07):** e2e login → refresh → gọi `/me` bằng access token cũ **ngay sau refresh, trước logout** → `401 UNAUTHENTICATED`; access token mới → 200.
- **Giữ nguyên reason khi revoke-all (FIX-14):** e2e tạo session đã LOGOUT trước, rồi replay một token ROTATED khác → assert session đã LOGOUT giữ nguyên reason LOGOUT, session ACTIVE chuyển REUSE_DETECTED, row bị replay giữ ROTATED.
- **Ràng buộc schema (FIX-09):** test migration D-15 — insert trực tiếp vi phạm CHECK (revoked_at có giá trị nhưng revoked_reason NULL; replaced_by_session_id đặt khi reason khác ROTATED) → DB từ chối; FK tự tham chiếu: xóa session mới → replaced_by_session_id của row cũ thành NULL (ON DELETE SET NULL).
- **Lý do thu hồi (FIX-09/AC-05/AC-06):** e2e ma trận 4 lý do thu hồi (ROTATED → TOKEN_REUSE_DETECTED; LOGOUT/LOGOUT_ALL/ADMIN_REVOKED → INVALID_REFRESH_TOKEN; REUSE_DETECTED → từ chối) + assert `revoked_reason` + `replaced_by_session_id` trong DB.
- **Session vô hiệu hóa access token (FIX-10/AC-07):** e2e login → refresh (cấp access mới) → logout session → gọi `/me` bằng **cả hai** access token (cũ trước refresh + mới sau refresh) → cả hai đều `401 UNAUTHENTICATED`.

## 13. Thay đổi API_SPEC/OpenAPI cần thực hiện (trong Giai đoạn 2 — chưa sửa tài liệu API trong Giai đoạn 1)

- **API_SPEC §11.7 logout:** ghi rõ ngữ nghĩa khi thiếu `refreshToken` (thu hồi toàn bộ session — FIX-06, ChatGPT đã duyệt về nguyên tắc); ghi rõ access token bị blacklist + mọi access token thuộc session đã logout đều hết hiệu lực nhờ kiểm tra `sid` (FIX-10).
- **API_SPEC §11.7 refresh:** thêm header `Idempotency-Key` bắt buộc (D-14); thiếu header → `400 VALIDATION_ERROR`; cùng token + cùng key → trả response đã lưu; cùng token + key khác → replay.
- **API_SPEC §2.3 claims:** access JWT thêm `type: "access"` + `sid`; refresh JWT: `sub`, `sid`, `type: "refresh"`, `iat`, `exp`.
- **API_SPEC §10.5/§16:** ghi chú rate limit refresh (D-05) + kiểm tra blacklist fail-closed 503 (D-06).
- **OpenAPI (`openapi.yaml`):** thêm parameter header `Idempotency-Key` cho `POST /auth/admin/refresh` (required); cập nhật mô tả `POST /auth/admin/logout` (ngữ nghĩa thiếu refreshToken); cập nhật schema token (claims `type`, `sid`); cập nhật mã lỗi `TOKEN_REUSE_DETECTED`/`INVALID_REFRESH_TOKEN` theo FIX-01/FIX-09.
