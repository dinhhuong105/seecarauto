## 2. Phạm vi triển khai

### 2.1 Đăng nhập — `POST /api/v1/auth/admin/login` (FR-090, FR-091)

- Request `{ username, password }` (bắt buộc). Response `200`: `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn: 900, admin: { id, username, roles: [...] } }` (API_SPEC §11.7, OpenAPI `/auth/admin/login`).
- Sai tài khoản/mật khẩu → `401 INVALID_CREDENTIALS`, message chung, không lộ tài khoản có tồn tại hay không (FR-090). Tài khoản không tồn tại vẫn chạy verify Argon2id với dummy hash để tránh rò rỉ qua thời gian phản hồi (đề xuất — xem §12 D-13).
- Tài khoản `isActive = false` → `401 INVALID_CREDENTIALS` chung, không lộ lý do.
- Đăng nhập thành công: reset `failedLoginAttempts` về 0; tạo 1 row `AdminRefreshSession` (chỉ lưu hash refresh token, `expiresAt` theo TTL đã chốt).

### 2.2 Refresh — `POST /api/v1/auth/admin/refresh` (FR-090)

- Request `{ refreshToken }`. Response `200`: access token mới + refresh token mới (xoay vòng); refresh token cũ bị thu hồi (`revoked_at` set, không xóa row — row cũ là bằng chứng cho reuse detection).
- **Claims của refresh JWT (FIX-07):** `sub` = admin id, `sid` = id của row `AdminRefreshSession` (liên kết token với session trong DB), `type: "refresh"` (phân biệt loại token), `iat`, `exp` (TTL đã chốt). Access JWT có `type: "access"` tương ứng (bổ sung nhỏ so với API_SPEC §2.3 — chỉ thêm claim `type`, không đổi các claim đã chốt) **và `sid` = id của session đã cấp token (FIX-10 — xem §2.3: guard kiểm tra trạng thái session)**. Verify refresh: (1) chữ ký bằng `JWT_REFRESH_SECRET`; (2) `type` phải là `"refresh"` — access token đưa vào `/refresh` → `401 INVALID_REFRESH_TOKEN` (không bao giờ chấp nhận token chỉ vì chữ ký hợp lệ); (3) `sid` phải khớp row session còn hiệu lực; (4) SHA-256 của toàn bộ JWT trình lên phải khớp `token_hash` của row. Guard `/me`/`/logout` từ chối refresh token (kiểm tra `type: "access"`).
- **Rotation nguyên tử (FIX-02):** trong một transaction duy nhất, conditional update `UPDATE admin_refresh_sessions SET revoked_at = now(), revoked_reason = 'ROTATED', replaced_by_session_id = $newSid WHERE id = $sid AND revoked_at IS NULL AND expires_at > now()` — chỉ request nào update được đúng 1 row mới được phát hành token mới. Request thua race xử lý theo Idempotency-Key D-14 (không dùng cửa sổ grace tự do — xem dưới). Không được chỉ dùng transaction thường rồi mặc định race đã giải quyết — phải có test đồng thời (AC-17).
- **Idempotency-Key cho refresh (D-14 — thay thế grace window, ChatGPT không duyệt grace nguyên trạng):** client gửi header `Idempotency-Key` (UUID, một key cho mỗi thao tác refresh; retry cùng thao tác dùng cùng key; thiếu header → `400 VALIDATION_ERROR`, details field `Idempotency-Key`). Backend lưu **kết quả thao tác đã phát hành** (cặp token mới) tạm thời trong Redis, TTL 10 giây, **mã hóa bằng encryption key riêng** (AES-256-GCM, IV ngẫu nhiên mỗi entry; không lưu refresh token plaintext trong DB hoặc log), key Redis = SHA-256 của (tokenHash cũ + Idempotency-Key). Cùng refresh token + cùng key → trả lại đúng response đã lưu (không rotation thêm, không revoke-all). Cùng refresh token + key khác → xử lý như replay (AC-05, revoke-all). Token khác + cùng key → thao tác khác, xử lý bình thường. Lý do ChatGPT bác grace tự do: DB chỉ lưu SHA-256 của refresh token (không đảo ngược được để trả lại token mới) và grace mở cho mọi request cho kẻ đánh cắp cơ hội nhận token mới.
- **Lý do thu hồi session (FIX-09):** mỗi lần thu hồi row `admin_refresh_sessions` phải ghi rõ `revoked_reason` (enum mới `RefreshSessionRevocationReason`: `ROTATED` | `LOGOUT` | `LOGOUT_ALL` | `ADMIN_REVOKED` | `REUSE_DETECTED`) + `replaced_by_session_id` (nullable, id của session mới khi rotation). Chỉ có `revoked_at` thì không phân biệt được rotation với logout — backend sẽ hoặc báo oan đánh cắp token, hoặc bỏ lọt replay. Quy tắc: `ROTATED` → kiểm tra replay (AC-05); các lý do còn lại → `401 INVALID_REFRESH_TOKEN` (AC-06); `REUSE_DETECTED` → từ chối token, session không được dùng tiếp. Cần **migration bổ sung riêng trong M02-05** (không sửa migration M02-01 đã nghiệm thu) — xem D-15, chờ Henry phê duyệt.
- **Phân biệt replay với hết hạn/thu hồi khác (FIX-01 + FIX-09):** trình lại token của row có `revoked_reason = ROTATED` → AC-05 (`401 TOKEN_REUSE_DETECTED` + revoke-all). Token hết hạn, hoặc row có `revoked_reason` khác (`LOGOUT`, `LOGOUT_ALL`, `ADMIN_REVOKED`) → `401 INVALID_REFRESH_TOKEN` (đăng nhập lại, AC-06). Row có `revoked_reason = REUSE_DETECTED` → từ chối, không dùng tiếp. Không tạo session mới khi refresh thất bại.

### 2.3 Logout — `POST /api/v1/auth/admin/logout` (FR-090)

- Header `Authorization: Bearer <access_token>` + body `{ refreshToken? }`. Response `204`.
- **Phạm vi logout (FIX-06):** logout **có gửi** `refreshToken` → thu hồi đúng session đó (refresh row revoked + access token blacklist) — logout một phiên. Logout **không gửi** `refreshToken` → thu hồi **toàn bộ session** của tài khoản (mọi row `admin_refresh_sessions` revoked) + blacklist access token — logout toàn bộ tài khoản (đề xuất; khác với cách đọc chữ §11.7 "refresh token (nếu gửi)" — vì nếu không gửi mà chỉ thu hồi access thì refresh session còn sống sẽ cấp access mới ngay, logout mất tác dụng; cần ChatGPT duyệt điểm này). Frontend logout chuẩn luôn gửi `refreshToken`; trường hợp không gửi (refresh đã mất/hết hạn) vẫn logout toàn bộ cho an toàn.
- **Thứ tự kiểm tra blacklist (FIX-03):** guard xác minh chữ ký + thời hạn JWT trước; **sau đó kiểm tra blacklist Redis trước khi chấp nhận request**; token trong blacklist → `401 UNAUTHENTICATED`. Redis lỗi khi kiểm tra blacklist → **fail-closed**: từ chối request bằng `503 SERVICE_UNAVAILABLE` + `Retry-After` (Error Catalog §11) — không được bỏ qua blacklist rồi chấp nhận token đã logout (AC-18).
- **Kiểm tra trạng thái session (FIX-10):** guard, sau khi verify chữ ký + thời hạn + blacklist, còn kiểm tra row session theo `sid` trong access JWT: session phải tồn tại, chưa revoked, chưa hết hạn — session đã revoked (bất kỳ lý do nào) → `401 UNAUTHENTICATED`. Nhờ đó logout một session vô hiệu hóa **mọi access token thuộc session đó** (kể cả access token cấp trước lần refresh gần nhất), không chỉ access token hiện tại. Access token không có `sid` (token cấp trước M02-05 — không tồn tại trong thực tế vì chưa có admin nào đăng nhập) → từ chối.
- **Cập nhật API_SPEC/OpenAPI (FIX-06):** API_SPEC §11.7 + OpenAPI phải ghi rõ ngữ nghĩa logout khi thiếu `refreshToken` (thu hồi toàn bộ session) — hiện spec chỉ ghi "refresh token (nếu gửi)". Xem §13.
- Thu hồi access token: lưu hash SHA-256 của access token vào Redis với TTL = thời gian còn lại tới `exp` (xem §12 D-06).
- Sau logout, access token cũ → `401 UNAUTHENTICATED`; refresh token cũ → `401 INVALID_REFRESH_TOKEN`.

### 2.4 Thông tin tài khoản — `GET /api/v1/auth/admin/me` (FR-081)

- Header `Authorization`. Response `200`: `{ id, username, roles: [{ id, name }], permissions: ["products.view", ...] }` — danh sách permission đã gộp vai trò + ngoại lệ từng tài khoản, deny (`granted = false`) thắng allow (API_SECURITY §2, `UserPermission`).
- Phân quyền resolve trực tiếp từ DB tại thời điểm request (cùng logic union mà middleware M02-06 sẽ tái dùng) — **không cần middleware RBAC trong M02-05** (xem §12 D-10).
- Thiếu token → `401 UNAUTHENTICATED`; access token hết hạn → `401 TOKEN_EXPIRED`.

### 2.5 Khóa tài khoản — FR-091 (ngưỡng do M02-05 chốt, chờ ChatGPT duyệt — §12 D-01)

- Sai liên tiếp tới ngưỡng → `423 ACCOUNT_LOCKED` + `retryAfter` (giây). Tài khoản đang bị khóa → `423` (kể cả khi mật khẩu đúng — theo FR-091 "báo rõ"; đánh đổi với FR-090 đã ghi ở §12 D-01).
- Mở khóa tự động sau thời gian khóa; Super Admin mở tay (API_SECURITY §1 — cơ chế mở tay thuộc M06-01/admin users, không thuộc M02-05).
- Trạng thái khóa dùng đúng 2 cột schema đã có: `users.failed_login_attempts` (CHECK ≥ 0) + `users.locked_until`.

### 2.6 Rate limit — tái dùng `RateLimitService` (M02-02)

- Login: `adminLoginIp` 5 lần/phút/IP + `adminLoginAccount` 10 lần/phút/tài khoản (fail-closed; Redis lỗi → fallback bộ nhớ tạm trong tiến trình, theo quyết định đã chốt ở M02-02 FIX-04).
- `GET /me` + `POST /logout` (đã đăng nhập): `adminAuthed` 300 lần/phút/tài khoản (fail-open theo rule hiện có).
- Refresh: chưa có kind riêng — đề xuất ở §12 D-05 (fail-closed vì refresh token tương đương credential).
- Vượt giới hạn → `429 RATE_LIMITED` + header `Retry-After` (Error Catalog §9).
- **Giới hạn của fallback bộ nhớ (FIX-04):** counter bộ nhớ chỉ dùng chung trong **một** backend instance, không chia sẻ giữa nhiều instance — không tuyên bố fallback bảo đảm rate limit toàn hệ thống; khi chạy đa instance, Redis là nguồn đúng duy nhất. AC-09/AC-10 kiểm tra đúng giới hạn này.

### 2.7 Cấu hình và secret

- Validate fail-fast lúc boot (theo mẫu `validateRedisEnv`/`validateMeilisearchEnv` trong `ConfigModule.forRoot`): `JWT_SECRET` và `JWT_REFRESH_SECRET` tối thiểu 32 ký tự ngẫu nhiên (API_SECURITY §1), `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` đúng định dạng thời gian; thiếu/sai → boot lỗi với message rõ ràng, không dùng secret mặc định trong code.
- `.env.example` (repo root) **đã có sẵn** 4 biến `JWT_SECRET`, `JWT_REFRESH_SECRET`, `JWT_EXPIRES_IN=15m`, `JWT_REFRESH_EXPIRES_IN=7d` (placeholder — TTL refresh 7d chưa phải quyết định đã chốt, xem §12 D-02). M02-05 chỉ xác minh + ghi tài liệu, không commit secret thật.
- Quy trình xoay JWT secret: API_SECURITY giao "M02 chốt" — đề xuất ở §12 D-11 (runbook, không code tự động xoay secret).
- **Tách biệt hai secret (FIX-05):** `JWT_SECRET` chỉ ký/xác minh access token; `JWT_REFRESH_SECRET` chỉ ký/xác minh refresh token; hai giá trị không được trùng nhau (config validation từ chối nếu trùng). Chi tiết thời gian chấp nhận secret cũ + xử lý session cũ khi xoay — xem §12 D-11.
- **Encryption key cho cache idempotency (D-14):** `REFRESH_IDEMPOTENCY_ENCRYPTION_KEY` (≥ 32 ký tự ngẫu nhiên, khác `JWT_SECRET` và `JWT_REFRESH_SECRET`; validate trong `validateAuthEnv`); dùng AES-256-GCM mã hóa response refresh lưu tạm trong Redis (TTL 10 giây). Không có key này → fail-fast khi khởi động.

## 3. Quy tắc kỹ thuật bắt buộc

- **Truyền token chỉ qua header `Authorization: Bearer`** (API_SECURITY §1): không nhận token qua query string, **không nhận token qua cookie cho API** (cookie chỉ dùng cho cart token). Response trả token trong JSON body theo API_SPEC §11.7 — mâu thuẫn với dòng "HttpOnly cookie" ở backlog M02-05, xem §12 D-04.
- **Refresh token chỉ lưu hash** (`admin_refresh_sessions.token_hash`, unique) — không lưu plaintext; không ghi token/mật khẩu/refresh token plaintext vào log (API_SPEC §12 "Không log").
- **Mật khẩu chỉ verify bằng Argon2id** với encoded hash ở `users.password_hash` (NFR-006); không trả hash trong bất kỳ response nào; không giới hạn độ dài tối đa thấp (tối thiểu 8 ký tự — API_SECURITY §1; chính sách cụ thể xem §12 D-07).
- **Không sửa schema/migration M02-01 đã nghiệm thu** nếu chưa chứng minh có thiếu sót và được ChatGPT duyệt (lệnh giao M02-05). Schema hiện tại đã đủ: `User` (passwordHash, isActive, failedLoginAttempts, lockedUntil), `AdminRefreshSession` (tokenHash unique, expiresAt, revokedAt), `Role`/`Permission`/`RolePermission`/`UserRole`/`UserPermission`, `AuditLog`.
- **Rotation nguyên tử:** conditional update trên session cũ trong transaction (FIX-02); không rotation trùng lặp khi refresh đồng thời.
- **Blacklist fail-closed:** guard kiểm tra blacklist sau khi verify JWT, trước khi chấp nhận request; Redis lỗi → `503 SERVICE_UNAVAILABLE`, không chấp nhận token đã logout (FIX-03).
- **Phân biệt loại token:** mọi verify đều kiểm tra claim `type` (`access`/`refresh`); không chấp nhận token sai loại dù chữ ký hợp lệ (FIX-07).
- **Audit trong cùng transaction:** audit lockout/reuse/revoke-all ghi trong cùng transaction nghiệp vụ với thao tác khóa/thu hồi (FIX-08); audit không chứa token/mật khẩu/hash.
- **Mỗi lần thu hồi session phải ghi rõ lý do:** `revoked_reason` (FIX-09) + `replaced_by_session_id` khi rotation; không suy luận lý do từ `revoked_at`.
- **Access JWT mang `sid`; guard kiểm tra trạng thái session:** session revoked/hết hạn → `401 UNAUTHENTICATED` (FIX-10).
- **Refresh yêu cầu `Idempotency-Key`:** thiếu header → `400 VALIDATION_ERROR`; cùng token + cùng key → trả response đã lưu; cùng token + key khác → replay (D-14).
- **Không làm middleware RBAC của M02-06.** M02-05 chỉ cần JWT AuthGuard (xác thực đã đăng nhập) cho `/me` và `/logout` — không kiểm tra permission (API_SPEC §10.5: 2 endpoint này yêu cầu `*` = đã đăng nhập bất kỳ).
- **Không tạo tài khoản admin mẫu hoặc secret giả** (bootstrap Super Admin là M06-01). Test tạo user trực tiếp bằng Prisma trong setup test với Argon2id hash thật — không có endpoint/seed tạo user trong code sản phẩm.
- **Không merge.** Không làm auth khách hàng (FR-093/FR-094, P1) và không làm M02-04 (chờ D-06).

### D-03 — Định danh đăng nhập: username hay email?

- Tài liệu: API_SPEC §11.7 ghi "username hoặc email" (M02 chốt); nhưng schema `User` **không có cột email** — chỉ có `username` unique.
- **Đề xuất:** đăng nhập bằng **username duy nhất**; sửa wording API_SPEC §11.7 thành username-only (không sửa schema). Nếu sau này cần login bằng email thì cần thêm cột + migration (không thuộc M02-05).

### D-04 — Vận chuyển token: Bearer body hay HttpOnly cookie?

- Mâu thuẫn tài liệu: backlog M02-05 ghi "HttpOnly cookie"; API_SPEC §11.7 trả token trong JSON body; API_SECURITY §1 quy định **chỉ Bearer header, không nhận token qua cookie cho API** (cookie chỉ dùng cho cart token).
- **Đề xuất:** theo API_SECURITY — **Bearer trong body, không cookie auth** (không dính CSRF qua cookie; không cần CSRF token cho auth endpoints). Sửa dòng backlog M02-05 bỏ "HttpOnly cookie". Cần ChatGPT xác nhận (đây là sửa tài liệu, không phải code).

### D-05 — Rate limit cho refresh

- Tài liệu: API_SPEC §16 có limit riêng cho login, không có limit riêng cho refresh; rule chung public POST là 30 lần/phút/IP (fail-open).
- **Đề xuất:** thêm 2 kind mới vào `RateLimitService` (mở rộng record hiện có, không sửa rule cũ): `adminRefreshIp` **30 lần/phút/IP** + `adminRefreshAccount` **10 lần/phút/tài khoản**, **fail-closed** (refresh token tương đương credential; Redis lỗi → fallback bộ nhớ tạm như login). Cần ChatGPT duyệt số + chính sách.

### D-06 — Blacklist access token khi logout

- Tài liệu: API_SPEC §11.7 yêu cầu thu hồi access token (blacklist tới khi hết hạn), nhưng không ghi cơ chế lưu; access token theo §2.3 chỉ chứa `sub`/role ids/`exp` (không có `jti`).
- **Đề xuất (đã bổ sung FIX-03):** lưu **hash SHA-256 của access token** vào Redis với TTL = thời gian còn lại tới `exp` (không cần thêm claim `jti`, không đổi spec token). Thứ tự guard: (1) verify chữ ký + thời hạn JWT; (2) kiểm tra blacklist Redis **trước khi chấp nhận request**; token trong blacklist → `401 UNAUTHENTICATED`; (3) Redis lỗi khi kiểm tra blacklist → **fail-closed**: từ chối bằng `503 SERVICE_UNAVAILABLE` + `Retry-After` (Error Catalog §11), không chấp nhận token đã logout. ChatGPT đề xuất trùng phương án này (27/11/2026) — chờ Henry duyệt.

### D-07 — Tham số Argon2id + chính sách mật khẩu

- Tài liệu: API_SECURITY §1 yêu cầu Argon2id, tối thiểu 8 ký tự, "M02 chốt chính sách cụ thể"; không ghi tham số memory/iterations/parallelism.
- **Đề xuất:** tham số OWASP khuyến nghị — **memory 19 MiB, iterations 2, parallelism 1, hash length 32**, định dạng encoded chuẩn của thư viện `argon2`; mật khẩu tối thiểu 8 ký tự, tối đa 128 ký tự, không quy tắc độ phức tạp bắt buộc (tránh khóa oan admin). Cần ChatGPT chốt tham số (thư viện `argon2` mặc định m=64 MiB/t=3/p=4 — nặng hơn; chọn OWASP để cân bằng hiệu năng login).

### D-08 — Ranh giới M02-05 với M08-06 (Argon2id + lockout)

- Tài liệu: backlog M08-06 "Argon2id + lockout — Hash mật khẩu Argon2id; khóa tài khoản sau N lần sai (FR-091)", High, **phụ thuộc M02-05**. Trùng tên với phần việc M02-05 đang làm (verify Argon2id + lockout FR-091).

Cần ChatGPT xác nhận ranh giới này để M02-05 không làm trùng/lấn M08-06.

### D-09 — Audit log cho sự kiện auth

- Tài liệu: không có yêu cầu tường minh nào bắt `AuditLog` ghi sự kiện login/logout/lockout (API_SPEC §2.3 chỉ ghi "logging/audit" chung; `AuditLog` hiện dùng cho FR-084 thay đổi permission).
- **Đề xuất (đã bổ sung FIX-08, Revision 03):** ghi audit cho **4 sự kiện** — (1) **khóa tài khoản** (FR-091): `actorId` = user id bị khóa — ghi rõ đây là **subject của sự kiện do hệ thống phát sinh** (không phải admin tự khóa mình; `AuditLog.actorId` bắt buộc + FK tới User nên không để null được), `entityId` = user id, `entityType` = `users`, `action` = `admin.locked`, `after` chỉ chứa số lần đăng nhập sai + thời điểm khóa; (2) **phát hiện reuse + revoke-all**: `actorId` = user id, `entityId` = user id, `action` = `auth.refresh_reuse_detected`, `after` = số session bị thu hồi (chỉ số lượng, không token/hash); (3) **logout một phiên**: `action` = `auth.logout_session`, `actorId` = `entityId` = user id, `after` = session id đã thu hồi (có ghi — logout là sự kiện bảo mật cần dấu vết); (4) **logout toàn bộ session**: `action` = `auth.logout_all_sessions`. Audit insert nằm **trong cùng transaction** với thao tác khóa/thu hồi (cùng commit hoặc cùng rollback — test phải chứng minh). Không ghi login thành công/thất bại thường. Không ghi token/mật khẩu/hash vào `before`/`after`. ChatGPT đồng ý có điều kiện (27/11/2026 ~14:10) + Henry đã duyệt D-09 (27/11/2026 ~14:07).

### D-10 — `/me` lấy roles/permissions khi RBAC middleware thuộc M02-06

- Tài liệu: API_SPEC §11.7 yêu cầu `/me` trả roles + permissions đã gộp; middleware kiểm tra permission thuộc M02-06.
- **Đề xuất:** `/me` resolve permission **trực tiếp từ DB** tại thời điểm request (union `role_permissions` + `user_permissions`, deny thắng allow) qua một hàm dùng chung (`permission.service` hoặc hàm trong `auth.service`) mà middleware M02-06 sẽ tái dùng sau — không triển khai guard kiểm tra permission trong M02-05. Cần ChatGPT xác nhận cách làm này.

### D-11 — Quy trình xoay JWT secret

- Tài liệu: API_SECURITY §1 "JWT secret tối thiểu 32 ký tự ngẫu nhiên, xoay định kỳ (quy trình xoay do M02 chốt)".
- **Đề xuất (đã bổ sung FIX-05 — tách riêng hai loại secret):** (1) **Access secret** (`JWT_SECRET`): ký access token; verify chấp nhận current + previous **tối đa 15 phút** sau xoay (1 chu kỳ access TTL), sau đó previous bị từ chối; gỡ previous khỏi config sau cửa sổ này. (2) **Refresh secret** (`JWT_REFRESH_SECRET`): ký refresh token; verify **chỉ chấp nhận current** (không previous — refresh sống 7 ngày, chấp nhận secret cũ 7 ngày là vô hiệu hóa việc xoay); khi xoay refresh secret, **toàn bộ refresh session cũ bị thu hồi** (mọi admin phải đăng nhập lại). (3) Hai secret không bao giờ trùng nhau (config validation từ chối nếu trùng). (4) Không giữ secret cũ vô thời hạn — runbook ghi rõ bước gỡ previous + thời điểm gỡ. Ghi quy trình vào `docs/infrastructure/AUTH_JWT.md`. ChatGPT đề xuất trùng hướng này (27/11/2026) — chờ Henry duyệt (đặc biệt: có chấp nhận bắt đăng nhập lại sau xoay refresh secret hay không).
- **Runbook lộ secret khẩn cấp (bổ sung Revision 03):** (1) xác nhận secret nào lộ; (2) xoay ngay secret đó (deploy secret mới làm current, secret cũ làm previous rồi gỡ theo cửa sổ overlap); (3) **thu hồi toàn bộ refresh session** (mọi admin đăng nhập lại); (4) ghi audit sự kiện lộ secret; (5) báo Henry + rà soát log truy cập bất thường. Rủi ro tồn dư đã ghi nhận: access token đã cấp bằng secret lộ vẫn dùng được tối đa 15 phút (tới khi hết hạn) vì không có danh sách thu hồi theo thời điểm cấp — chấp nhận rủi ro này, không thêm cơ chế "reject token cấp trước thời điểm X" trong M02-05.

### D-14 — Chống double-submit khi refresh (thay thế grace window — Revision 03)

- Vấn đề: trình duyệt gửi 2 request refresh đồng thời (double-submit/retry) — request thua race trình lại token vừa bị rotation; nếu coi mọi replay là đánh cắp thì logout oan user hợp lệ.
- **Grace window 10 giây (Revision 02) — ChatGPT KHÔNG DUYỆT nguyên trạng (27/11/2026 ~14:10):** (A) DB chỉ lưu SHA-256 của refresh token, không đảo ngược được để trả lại cặp token mới; (B) grace mở cho mọi request — kẻ đánh cắp trình lại token trong 10 giây cũng nhận được token mới, làm suy yếu phát hiện reuse.
- **Đề xuất thay thế (Revision 03): Idempotency-Key cho refresh.** Client tạo một UUID cho mỗi thao tác refresh, gửi qua header `Idempotency-Key`; retry cùng thao tác dùng cùng key; thiếu header → `400 VALIDATION_ERROR` (details field `Idempotency-Key`). Backend lưu kết quả thao tác đã phát hành (cặp token mới) tạm thời trong Redis, TTL 10 giây, **mã hóa AES-256-GCM** bằng encryption key riêng (`REFRESH_IDEMPOTENCY_ENCRYPTION_KEY`, ≥ 32 ký tự, khác hai JWT secret); không lưu refresh token plaintext trong DB hoặc log. Cùng token + cùng key → trả lại đúng response đã lưu. Cùng token + key khác → replay, revoke-all (AC-05). Key Redis = SHA-256 của (tokenHash cũ + Idempotency-Key). Cần cập nhật API_SPEC §11.7 + OpenAPI (xem §13) và test tương ứng (AC-17).
- **Chờ ChatGPT duyệt phương án thay thế này.**

## 13. Thay đổi API_SPEC/OpenAPI cần thực hiện (trong Giai đoạn 2 — chưa sửa tài liệu API trong Giai đoạn 1)

- **API_SPEC §11.7 logout:** ghi rõ ngữ nghĩa khi thiếu `refreshToken` (thu hồi toàn bộ session — FIX-06, ChatGPT đã duyệt về nguyên tắc); ghi rõ access token bị blacklist + mọi access token thuộc session đã logout đều hết hiệu lực nhờ kiểm tra `sid` (FIX-10).
- **API_SPEC §11.7 refresh:** thêm header `Idempotency-Key` bắt buộc (D-14); thiếu header → `400 VALIDATION_ERROR`; cùng token + cùng key → trả response đã lưu; cùng token + key khác → replay.
- **API_SPEC §2.3 claims:** access JWT thêm `type: "access"` + `sid`; refresh JWT: `sub`, `sid`, `type: "refresh"`, `iat`, `exp`.
- **API_SPEC §10.5/§16:** ghi chú rate limit refresh (D-05) + kiểm tra blacklist fail-closed 503 (D-06).
- **OpenAPI (`openapi.yaml`):** thêm parameter header `Idempotency-Key` cho `POST /auth/admin/refresh` (required); cập nhật mô tả `POST /auth/admin/logout` (ngữ nghĩa thiếu refreshToken); cập nhật schema token (claims `type`, `sid`); cập nhật mã lỗi `TOKEN_REUSE_DETECTED`/`INVALID_REFRESH_TOKEN` theo FIX-01/FIX-09.
- **Ghi chú:** Giai đoạn 1 chỉ liệt kê thay đổi cần làm — không sửa `docs/api/` trong Revision 03; việc sửa API_SPEC/OpenAPI thuộc Giai đoạn 2 (cùng với code + test).
