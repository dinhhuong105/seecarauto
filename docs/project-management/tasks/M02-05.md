## 1. Mục tiêu

Triển khai xác thực admin cho backend NestJS: đăng nhập bằng username + mật khẩu (Argon2id), access JWT 15 phút + refresh token xoay vòng (hash trong DB, thu hồi từng session, phát hiện reuse), logout thu hồi cả hai token, endpoint `/me` trả thông tin tài khoản + quyền đã gộp — đúng API_SPEC §11.7, API_SECURITY §1, Error Catalog, FR-090/FR-091.

## 2. Phạm vi triển khai

### 2.1 Đăng nhập — `POST /api/v1/auth/admin/login` (FR-090, FR-091)

- Request `{ username, password }` (bắt buộc). Response `200`: `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn: 900, admin: { id, username, roles: [...] } }` (API_SPEC §11.7, OpenAPI `/auth/admin/login`).
- Sai tài khoản/mật khẩu → `401 INVALID_CREDENTIALS`, message chung, không lộ tài khoản có tồn tại hay không (FR-090). Tài khoản không tồn tại vẫn chạy verify Argon2id với dummy hash để tránh rò rỉ qua thời gian phản hồi (đề xuất — xem §12 D-13).
- Tài khoản `isActive = false` → `401 INVALID_CREDENTIALS` chung, không lộ lý do.
- Đăng nhập thành công: reset `failedLoginAttempts` về 0; tạo 1 row `AdminRefreshSession` (chỉ lưu hash refresh token, `expiresAt` theo TTL đã chốt).

### 2.2 Refresh — `POST /api/v1/auth/admin/refresh` (FR-090)

- Request `{ refreshToken }`. Response `200`: access token mới + refresh token mới (xoay vòng); refresh token cũ bị thu hồi (`revoked_at` set, không xóa row — row cũ là bằng chứng cho reuse detection).
- Refresh token đã thu hồi/hết hạn → `401 INVALID_REFRESH_TOKEN` (đăng nhập lại).
- Refresh token đã dùng rồi (replay — hash khớp row đã revoked) → thu hồi **toàn bộ session** của tài khoản + `401 TOKEN_REUSE_DETECTED` (nghi ngờ đánh cắp token, API_SECURITY §1).
- Không tạo session mới khi refresh thất bại.

### 2.3 Logout — `POST /api/v1/auth/admin/logout` (FR-090)

- Header `Authorization: Bearer <access_token>` + body `{ refreshToken? }`. Response `204`.
- Thu hồi access token hiện tại (blacklist tới khi hết hạn — đề xuất lưu hash token vào Redis với TTL = thời gian còn lại của token, xem §12 D-06) và refresh token (nếu gửi).
- Sau logout, access token cũ → `401 UNAUTHENTICATED`; refresh token cũ → `401 INVALID_REFRESH_TOKEN`.
- Logout không gửi `refreshToken` vẫn thu hồi access token.

### 2.4 Thông tin tài khoản — `GET /api/v1/auth/admin/me` (FR-081)

- Header `Authorization`. Response `200`: `{ id, username, roles: [{ id, name }], permissions: ["products.view", ...] }` — danh sách permission đã gộp vai trò + ngoại lệ từng tài khoản, deny (`granted = false`) thắng allow (API_SECURITY §2, `UserPermission`).
- Phân quyền resolve trực tiếp từ DB tại thời điểm request (cùng logic union mà middleware M02-06 sẽ tái dùng) — **không cần middleware RBAC trong M02-05** (xem §12 D-10).
- Thiếu token → `401 UNAUTHENTICATED`; access token hết hạn → `401 TOKEN_EXPIRED`.

### 2.5 Khóa tài khoản — FR-091 (ngưỡng do M02-05 chốt, chờ ChatGPT duyệt — §12 D-01)

- Sai liên tiếp tới ngưỡng → `423 ACCOUNT_LOCKED` + `retryAfter` (giây). Tài khoản đang bị khóa → `423` (kể cả khi mật khẩu đúng — theo FR-091 "báo rõ"; đánh đổi với FR-090 đã ghi ở §12 D-01).
- Mở khóa tự động sau thời gian khóa; Super Admin mở tay (API_SECURITY §1 — cơ chế mở tay thuộc M06-01/admin users, không thuộc M02-05).
- Trạng thái khóa dùng đúng 2 cột schema đã có: `users.failed_login_attempts` (CHECK ≥ 0) + `users.locked_until`.

### 2.6 Rate limit — tái dùng `RateLimitService` (M02-02)

- Login: `adminLoginIp` 5 lần/phút/IP + `adminLoginAccount` 10 lần/phút/tài khoản (fail-closed; Redis lỗi → fallback bộ nhớ tạm trong tiến trình, theo quyết định đã chốt ở M02-02 FIX-04).
- `GET /me` + `POST /logout` (đã đăng nhập): `adminAuthed` 300 lần/phút/tài khoản (fail-open theo rule hiện có).
- Refresh: chưa có kind riêng — đề xuất ở §12 D-05 (fail-closed vì refresh token tương đương credential).
- Vượt giới hạn → `429 RATE_LIMITED` + header `Retry-After` (Error Catalog §9).

### 2.7 Cấu hình và secret

- Validate fail-fast lúc boot (theo mẫu `validateRedisEnv`/`validateMeilisearchEnv` trong `ConfigModule.forRoot`): `JWT_SECRET` và `JWT_REFRESH_SECRET` tối thiểu 32 ký tự ngẫu nhiên (API_SECURITY §1), `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` đúng định dạng thời gian; thiếu/sai → boot lỗi với message rõ ràng, không dùng secret mặc định trong code.
- `.env.example` (repo root) **đã có sẵn** 4 biến `JWT_SECRET`, `JWT_REFRESH_SECRET`, `JWT_EXPIRES_IN=15m`, `JWT_REFRESH_EXPIRES_IN=7d` (placeholder — TTL refresh 7d chưa phải quyết định đã chốt, xem §12 D-02). M02-05 chỉ xác minh + ghi tài liệu, không commit secret thật.
- Quy trình xoay JWT secret: API_SECURITY giao "M02 chốt" — đề xuất ở §12 D-11 (runbook, không code tự động xoay secret).

### 2.8 Ánh xạ lỗi

- Mọi lỗi auth theo đúng Error Catalog: `UNAUTHENTICATED` / `INVALID_CREDENTIALS` / `TOKEN_EXPIRED` / `INVALID_REFRESH_TOKEN` / `TOKEN_REUSE_DETECTED` (401), `FORBIDDEN` (403, chỉ dùng khi có permission check — không thuộc M02-05), `ACCOUNT_LOCKED` + `retryAfter` (423), `RATE_LIMITED` + `Retry-After` (429). Message tiếng Việt theo Catalog; không lộ stack trace, SQL, tên bảng/cột, secret (API_SPEC §11.7/§12).

## 3. Quy tắc kỹ thuật bắt buộc

- **Truyền token chỉ qua header `Authorization: Bearer`** (API_SECURITY §1): không nhận token qua query string, **không nhận token qua cookie cho API** (cookie chỉ dùng cho cart token). Response trả token trong JSON body theo API_SPEC §11.7 — mâu thuẫn với dòng "HttpOnly cookie" ở backlog M02-05, xem §12 D-04.
- **Refresh token chỉ lưu hash** (`admin_refresh_sessions.token_hash`, unique) — không lưu plaintext; không ghi token/mật khẩu/refresh token plaintext vào log (API_SPEC §12 "Không log").
- **Mật khẩu chỉ verify bằng Argon2id** với encoded hash ở `users.password_hash` (NFR-006); không trả hash trong bất kỳ response nào; không giới hạn độ dài tối đa thấp (tối thiểu 8 ký tự — API_SECURITY §1; chính sách cụ thể xem §12 D-07).
- **Không sửa schema/migration M02-01 đã nghiệm thu** nếu chưa chứng minh có thiếu sót và được ChatGPT duyệt (lệnh giao M02-05). Schema hiện tại đã đủ: `User` (passwordHash, isActive, failedLoginAttempts, lockedUntil), `AdminRefreshSession` (tokenHash unique, expiresAt, revokedAt), `Role`/`Permission`/`RolePermission`/`UserRole`/`UserPermission`, `AuditLog`.
- **Không làm middleware RBAC của M02-06.** M02-05 chỉ cần JWT AuthGuard (xác thực đã đăng nhập) cho `/me` và `/logout` — không kiểm tra permission (API_SPEC §10.5: 2 endpoint này yêu cầu `*` = đã đăng nhập bất kỳ).
- **Không tạo tài khoản admin mẫu hoặc secret giả** (bootstrap Super Admin là M06-01). Test tạo user trực tiếp bằng Prisma trong setup test với Argon2id hash thật — không có endpoint/seed tạo user trong code sản phẩm.
- **Không merge.** Không làm auth khách hàng (FR-093/FR-094, P1) và không làm M02-04 (chờ D-06).

## 12. Điểm chưa quyết định — cần ChatGPT duyệt trước khi code

**Không tự đặt ra chính sách bảo mật nếu tài liệu chưa quyết định.** Mỗi điểm dưới đây có đề xuất của Muse + lý do; ChatGPT chốt số/phương án cuối cùng.

### D-01 — FR-091: ngưỡng khóa + thời gian khóa

- Tài liệu: API_SPEC §11.7 + API_SECURITY §1 đều giao "ngưỡng do M02 chốt"; Error Catalog ví dụ `retryAfter: 900` (15 phút) — chỉ là ví dụ, chưa phải quyết định.
- **Đề xuất:** sai liên tiếp **5 lần** → khóa **15 phút** (`retryAfter: 900`); đăng nhập đúng reset counter về 0; hết 15 phút tự mở; Super Admin mở tay (cơ chế mở tay thuộc M06-01). Lý do: 5 lần khớp ngưỡng rate limit tài khoản (10 lần/phút) mà không khóa oan người gõ sai 1–2 lần; 15 phút khớp ví dụ Catalog.
- **Đánh đổi cần ChatGPT chấp nhận:** tài khoản đang khóa → trả `423` ngay (kể cả khi mật khẩu đúng) theo FR-091 "báo rõ" — điều này lộ rằng tài khoản tồn tại + đang khóa, mâu thuẫn một phần với FR-090 (không lộ tài khoản có tồn tại). Đề xuất giữ `423` vì FR-091 yêu cầu báo rõ và spec đã chốt status này; kẻ tấn công đã biết tài khoản tồn tại từ trước khi khóa (phải sai 5 lần mới khóa).

### D-02 — Refresh token TTL

- Tài liệu: API_SPEC không ghi số ngày cụ thể cho refresh TTL; `.env.example` đã có `JWT_REFRESH_EXPIRES_IN=7d` (placeholder, chưa phải quyết định).
- **Đề xuất:** giữ **7 ngày** (chuẩn thông dụng cho admin panel; access 15 phút + refresh 7 ngày). Cần ChatGPT xác nhận 7d là số chốt, hoặc đổi số khác.

### D-03 — Định danh đăng nhập: username hay email?

- Tài liệu: API_SPEC §11.7 ghi "username hoặc email" (M02 chốt); nhưng schema `User` **không có cột email** — chỉ có `username` unique.
- **Đề xuất:** đăng nhập bằng **username duy nhất**; sửa wording API_SPEC §11.7 thành username-only (không sửa schema). Nếu sau này cần login bằng email thì cần thêm cột + migration (không thuộc M02-05).

### D-04 — Vận chuyển token: Bearer body hay HttpOnly cookie?

- Mâu thuẫn tài liệu: backlog M02-05 ghi "HttpOnly cookie"; API_SPEC §11.7 trả token trong JSON body; API_SECURITY §1 quy định **chỉ Bearer header, không nhận token qua cookie cho API** (cookie chỉ dùng cho cart token).
- **Đề xuất:** theo API_SECURITY — **Bearer trong body, không cookie auth** (không dính CSRF qua cookie; không cần CSRF token cho auth endpoints). Sửa dòng backlog M02-05 bỏ "HttpOnly cookie". Cần ChatGPT xác nhận (đây là sửa tài liệu, không phải code).

### D-05 — Rate limit cho refresh

- Tài liệu: API_SPEC §16 có limit riêng cho login, không có limit riêng cho refresh; rule chung public POST là 30 lần/phút/IP (fail-open).
- **Đề xuất:** thêm 2 kind mới vào `RateLimitService` (mở rộng record hiện có, không sửa rule cũ): `adminRefreshIp` **30 lần/phút/IP** + `adminRefreshAccount` **10 lần/phút/tài khoản**, **fail-closed** (refresh token tương đương credential; Redis lỗi → fallback bộ nhớ tạm như login). Cần ChatGPT duyệt số + chính sách.

### D-06 — Blacklist access token khi logout

- Tài liệu: API_SPEC §11.7 yêu cầu thu hồi access token (blacklist tới khi hết hạn), nhưng không ghi cơ chế lưu; access token theo §2.3 chỉ chứa `sub`/role ids/`exp` (không có `jti`).
- **Đề xuất:** lưu **hash SHA-256 của access token** vào Redis với TTL = thời gian còn lại tới `exp` (không cần thêm claim `jti`, không đổi spec token); guard kiểm tra blacklist trước khi chấp nhận token. Cần ChatGPT duyệt cơ chế này (thay cho phương án chấp nhận rủi ro 15 phút còn lại của access token sau logout).

### D-07 — Tham số Argon2id + chính sách mật khẩu

- Tài liệu: API_SECURITY §1 yêu cầu Argon2id, tối thiểu 8 ký tự, "M02 chốt chính sách cụ thể"; không ghi tham số memory/iterations/parallelism.
- **Đề xuất:** tham số OWASP khuyến nghị — **memory 19 MiB, iterations 2, parallelism 1, hash length 32**, định dạng encoded chuẩn của thư viện `argon2`; mật khẩu tối thiểu 8 ký tự, tối đa 128 ký tự, không quy tắc độ phức tạp bắt buộc (tránh khóa oan admin). Cần ChatGPT chốt tham số (thư viện `argon2` mặc định m=64 MiB/t=3/p=4 — nặng hơn; chọn OWASP để cân bằng hiệu năng login).

### D-08 — Ranh giới M02-05 với M08-06 (Argon2id + lockout)

- Tài liệu: backlog M08-06 "Argon2id + lockout — Hash mật khẩu Argon2id; khóa tài khoản sau N lần sai (FR-091)", High, **phụ thuộc M02-05**. Trùng tên với phần việc M02-05 đang làm (verify Argon2id + lockout FR-091).
- **Đề xuất ranh giới:** M02-05 làm **đường verify + state machine lockout** phục vụ login (dùng `password.service` verify + `failedLoginAttempts`/`lockedUntil`); M08-06 làm **hardening**: chính sách tạo/đổi mật khẩu, review tham số Argon2id, review ngưỡng khóa, runbook xoay secret (D-11), kiểm thử tấn công (brute-force/timing). Cần ChatGPT xác nhận ranh giới này để M02-05 không làm trùng/lấn M08-06.

### D-09 — Audit log cho sự kiện auth

- Tài liệu: không có yêu cầu tường minh nào bắt `AuditLog` ghi sự kiện login/logout/lockout (API_SPEC §2.3 chỉ ghi "logging/audit" chung; `AuditLog` hiện dùng cho FR-084 thay đổi permission).
- **Đề xuất:** ghi audit cho 3 sự kiện: **khóa tài khoản** (FR-091), **phát hiện reuse refresh token** (nghi đánh cắp), **logout thu hồi toàn bộ session** (khi reuse). Không ghi login thành công/thất bại thường (tránh phình log). Không ghi token/mật khẩu vào `before`/`after` (API_SPEC: không lưu PII/token/secret trong audit). Cần ChatGPT duyệt danh sách sự kiện.

### D-10 — `/me` lấy roles/permissions khi RBAC middleware thuộc M02-06

- Tài liệu: API_SPEC §11.7 yêu cầu `/me` trả roles + permissions đã gộp; middleware kiểm tra permission thuộc M02-06.
- **Đề xuất:** `/me` resolve permission **trực tiếp từ DB** tại thời điểm request (union `role_permissions` + `user_permissions`, deny thắng allow) qua một hàm dùng chung (`permission.service` hoặc hàm trong `auth.service`) mà middleware M02-06 sẽ tái dùng sau — không triển khai guard kiểm tra permission trong M02-05. Cần ChatGPT xác nhận cách làm này.

### D-11 — Quy trình xoay JWT secret

- Tài liệu: API_SECURITY §1 "JWT secret tối thiểu 32 ký tự ngẫu nhiên, xoay định kỳ (quy trình xoay do M02 chốt)".
- **Đề xuất (runbook, không code tự động xoay):** hỗ trợ 2 secret (current + previous) trong config để xoay không downtime — deploy secret mới làm current, secret cũ làm previous trong 1 chu kỳ access TTL (15 phút) rồi gỡ; refresh token phải đăng nhập lại sau xoay (refresh secret xoay đồng thời); ghi quy trình vào `docs/infrastructure/AUTH_JWT.md`. Cần ChatGPT duyệt (đặc biệt: có chấp nhận bắt đăng nhập lại sau xoay refresh secret hay không).

### D-12 — Thư viện JWT + Argon2id

- Hiện trạng: `backend/package.json` chưa có `@nestjs/jwt`, `argon2`, `passport`, `jsonwebtoken` (đã kiểm tra 27/11/2026).
- **Đề xuất:** `@nestjs/jwt` (chuẩn NestJS, dùng `jsonwebtoken` bên dưới) + `argon2` (binding Argon2id chính thức), pin exact theo quy ước repo. Không dùng Passport (chỉ cần Bearer guard tự viết, tránh thêm abstraction). Cần ChatGPT duyệt lựa chọn thư viện.

### D-13 — Chống rò rỉ qua thời gian phản hồi (timing)

- Tài liệu: FR-090 chỉ yêu cầu message chung, không đề cập timing.
- **Đề xuất:** khi username không tồn tại, vẫn chạy verify Argon2id với **dummy hash cố định** (chi phí ~ bằng verify thật) rồi mới trả `401` — tránh kẻ tấn công phân biệt tài khoản tồn tại qua thời gian phản hồi. Chi phí: +1 lần hash mỗi lần login sai user (không đáng kể). Cần ChatGPT duyệt (đây là biện pháp phòng thủ bổ sung ngoài spec).
