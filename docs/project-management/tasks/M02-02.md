## 2. Phạm vi được phép

### 2.1 Redis infrastructure

- Cài Redis client tương thích với BullMQ.
- Pin version cụ thể, không dùng latest.
- Xây dựng RedisModule/RedisService tích hợp NestJS.
- Quản lý kết nối, reconnect, timeout, graceful shutdown.
- Đọc cấu hình từ environment.
- Có health/readiness check cho Redis.
- Không tạo nhiều Redis connection tùy tiện ở từng module.
- Redis hiện đã được khai báo trong docker-compose.yml với Redis 7 Alpine, port 6379, volume persistence và health check. Tận dụng cấu hình hiện có; chỉ sửa nếu có lý do kỹ thuật cụ thể.

### 2.2 Cache service

Triển khai cache-aside service có API thống nhất: get; set; delete; deleteByPattern hoặc cơ chế invalidate namespace an toàn; remember (cache miss → lấy dữ liệu nguồn → lưu cache); Versioned namespace; Chống cache stampede; Xử lý serialization/deserialization; Timeout và fallback khi Redis lỗi.

Key phải có namespace thống nhất: `seecarauto:<module>:<entity>:<id>`.
Ví dụ: `seecarauto:products:detail:{productId}`; `seecarauto:categories:detail:{categoryId}`; `seecarauto:search:results:{queryHash}`.
Không lưu mật khẩu, JWT, refresh token plaintext, thông tin khách hàng nhạy cảm hoặc thông tin xác thực trong cache.

### 2.3 Cache TTL

Tuân thủ ADR-006 và NFR-005:

- Danh mục: 3.600 giây
- Thương hiệu: 21.600 giây
- Chi tiết sản phẩm: 900 giây
- Danh sách sản phẩm: 300–900 giây
- Hãng xe / dòng xe: 86.400 giây
- Kết quả tìm kiếm: 60–300 giây
- SEO metadata: 3.600 giây
- Cấu hình website: 3.600 giây
- Quyền người dùng: 300 giây
- Tồn kho: 30–60 giây

Yêu cầu: Đưa TTL vào cấu hình dùng chung trong packages/shared hoặc vị trí phù hợp với cấu trúc monorepo. Không để mỗi module tự khai báo TTL rời rạc. Các TTL có khoảng giá trị phải có cấu hình mặc định được ghi rõ, nằm trong khoảng đã được duyệt. Có unit test đối chiếu toàn bộ TTL với NFR-005. Invalidation phải được hỗ trợ khi dữ liệu được Admin cập nhật. Không sửa API contract hoặc tự triển khai CRUD sản phẩm trong task này.

### 2.4 Redis Cart Storage — G-03

Triển khai lớp lưu trữ giỏ hàng guest trên Redis.

Yêu cầu:

- Key được định danh bằng opaque, high-entropy random cart token do server cấp.
- Không sử dụng user ID, email, số điện thoại hoặc dữ liệu dễ đoán làm token.
- Có thể dùng hash của token để tạo Redis key, tránh lộ token gốc trong key/log.
- TTL mặc định 30 ngày, theo API Specification §11.1.
- TTL phải có cấu hình environment, không rải literal 30 ngày trong code.
- Khi đọc/ghi giỏ, phải làm mới TTL theo chính sách đã định.
- Hỗ trợ thêm, đọc, cập nhật và xóa cart ở mức storage adapter.
- Dữ liệu cart phải đáp ứng cấu trúc cần thiết để M05 triển khai API Cart.
- Không tự thay đổi cách tính giá, kiểm tra tồn kho hoặc checkout.
- Không ghi cart token vào application log.

Lưu ý quan trọng: API Specification quy định giá và tình trạng sản phẩm phải được server kiểm tra lại khi checkout. Cart không phải nguồn sự thật về giá cuối cùng.

Khi Redis lỗi: Cart có thể tạm thời không truy cập được. Không tự chuyển sang lưu PostgreSQL vì chưa có quyết định về cơ chế fallback cart. Trả lỗi dependency phù hợp theo API contract; không giả vờ trả về giỏ rỗng rồi làm mất dữ liệu.

### 2.5 Redis Rate Limiting

Triển khai Redis-backed counter store có thao tác atomic.

Các giới hạn theo API Specification §16:

- Public GET: 100 request/phút/IP
- Public write: 30 request/phút/IP
- Admin login: 5 lần/phút/IP và 10 lần/phút/tài khoản
- Order lookup: 10 lần/phút/IP và 5 lần/phút/mã đơn
- Search / suggest: 60 lần/phút/IP
- Contact: 5 lần/giờ/IP
- Create order: 10 lần/phút/cartToken
- Admin đã đăng nhập: 300 request/phút/tài khoản

Yêu cầu: Counter phải atomic, không dùng chuỗi thao tác INCR/EXPIRE thiếu bảo đảm. Có key namespace riêng cho từng loại giới hạn. Có unit test và integration test. Hỗ trợ trả thông tin limit/remaining/reset để tầng HTTP sử dụng. Không triển khai toàn bộ guard/controller nghiệp vụ thuộc M02-05 hoặc M05.

Chính sách Redis lỗi theo API Specification: Public GET: fail-open. Login và order lookup: fail-closed đối với Redis, nhưng phải có fallback giới hạn tạm thời bằng bộ nhớ backend theo API Specification. Phải ghi rõ fallback in-memory chỉ có tính chất tạm thời, không đảm bảo chia sẻ giữa nhiều backend instances.

### 2.6 BullMQ infrastructure

Triển khai BullMQ dùng Redis hiện có.

Yêu cầu: Queue module dùng chung trong NestJS. Có cơ chế đăng ký queue và worker thống nhất. Producer/consumer có thể tái sử dụng từ các task tiếp theo. Cấu hình retry, backoff, concurrency và retention. Có xử lý lỗi job và khả năng quan sát trạng thái queue. Graceful shutdown để không bỏ dở job đang xử lý. Có job test thực tế chứng minh enqueue → process → complete. Có quy tắc chống xử lý trùng ở mức job ID/idempotency phù hợp.

Định hướng queue: catalog-sync — Đồng bộ thay đổi catalogue sang Meilisearch — Hạ tầng và contract; consumer nghiệp vụ thuộc M02-03. seo-jobs — Job SEO nền — Chỉ chuẩn bị khả năng đăng ký; không gọi AI provider. Queue test — Kiểm thử queue infrastructure — Được phép triển khai đầy đủ.

Các mặc định kỹ thuật ban đầu có thể dùng: Retry: 3 lần. Backoff: exponential, khởi đầu 1 giây. Giữ lại một lượng job completed/failed có giới hạn để debug. Concurrency cấu hình qua environment. Đây là mặc định kỹ thuật cho infrastructure, không phải cam kết SLA hoặc chính sách nghiệp vụ. Ghi lại trong tài liệu để có thể điều chỉnh.

Không triển khai trong M02-02: Meilisearch indexing thực tế; AI SEO hoặc AI provider; Email/Zalo notification; Order processing nghiệp vụ; Cron nghiệp vụ chưa có yêu cầu.
