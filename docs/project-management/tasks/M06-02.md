## 2. Phạm vi triển khai

### 2.1 Endpoint — ownership đã chốt theo RB-15 (M02-06 §12, §2.9)

Bảng dưới đây là phân công **đã quyết định** (ChatGPT 28/11/2026, RB-15) — brief này không đổi ownership. 7 operation role/permission trong OpenAPI (đếm thật bằng script, xem §10): 6 thuộc M06-02, 1 thuộc M06-03. Ranh giới M06-02/M06-03 còn một điểm chưa rõ — xem GAP-01/GAP-06 (§12).

| Method + Path | Permission | FR | Thuộc task | Ghi chú |
| --- | --- | --- | --- | --- |
| `GET /api/v1/roles` | `roles.view` | FR-080, FR-082 | **M06-02** | Danh sách vai trò, phân trang (API_SPEC §13) |
| `POST /api/v1/roles` | `roles.create` | FR-082 | **M06-02** | Tạo vai trò `{ name, description }` |
| `PATCH /api/v1/roles/{roleId}` | `roles.update` | FR-082 | **M06-02** | Sửa tên/mô tả vai trò |
| `DELETE /api/v1/roles/{roleId}` | `roles.delete` | FR-082, FR-085 | **M06-02** | Xóa vai trò; chặn khi là vai trò của Super Admin cuối cùng → `403 LAST_SUPER_ADMIN_ROLE` (GAP-02) |
| `GET /api/v1/roles/{roleId}/permissions` | `roles.view` | FR-080 | **M06-02** | Ma trận quyền của một vai trò |
| `PUT /api/v1/roles/{roleId}/permissions` | `roles.update` | FR-080, FR-081, FR-084 | **M06-02** | Cập nhật toàn bộ ma trận; `If-Match` bắt buộc; chặn khi khiến Super Admin cuối cùng mất quyền → `403 LAST_SUPER_ADMIN` (GAP-02) |
| `GET /api/v1/permissions` | `roles.view` | FR-080 | M06-03 | Danh sách toàn bộ permission code theo module — **không** thuộc M06-02 |

- **Body đã chốt (API_SPEC §11.6, OpenAPI):** `POST /roles` `{ name (bắt buộc, minLength 1), description (string | null) }` → `201 { data: Role }`. `PATCH /roles/{roleId}` `{ name?, description? }` → `200 { data: Role }`. `DELETE /roles/{roleId}` → `204` (không body). `GET /roles/{roleId}/permissions` → `200 { data: { roleId, permissions: [{ module, action, granted }] } }`. `PUT /roles/{roleId}/permissions` `{ permissions: [{ module, action, granted }] }` (thay **toàn bộ** ma trận của role) → `200 { data: { roleId, permissions: [...] } }`; header `If-Match: <etag>` **bắt buộc** (API_SPEC §15).
- **Response Role (OpenAPI schema `Role`):** `{ id (uuid), name, description (string | null) }` — không có trường `userCount` trong contract hiện tại (xem GAP-07).
- **Không có endpoint:** `GET /users`, `POST /users`, `GET /users/{userId}`, `GET /users/{userId}/roles` — đã xác minh trong OpenAPI (M02-06 §2.9). RBAC chỉ thao tác trên tài khoản đã tồn tại (tạo bởi bootstrap M06-01); màn hình `/users` là PROVISIONAL (RBAC Matrix §6).

### 2.2 Backend — triển khai trên nền tảng M02-06, không viết lại

- **Module mới `RolesModule`** (`backend/src/roles/`): `RolesController` + `RolesService` + DTOs; import `RbacModule` (đã export `PermissionsGuard`, `RbacAuditService`, `RbacService` — RBAC.md §9) và `AuthModule` (tái dùng `JwtAuthGuard`). Không tạo module guard/audit/service thứ hai.
- **Guard xếp chồng trên từng handler:** `@UseGuards(JwtAuthGuard, PermissionsGuard)` + `@RequirePermission(code)` với đúng code trong OpenAPI (bảng §2.1). Không gắn guard global (kẻo chặn nhầm endpoint public — RB-09). Handler không có metadata → `403` fail-closed (hành vi của `PermissionsGuard` M02-06).
- **Tạo/sửa/xóa role — `RolesService` mới:** `POST` tạo row `Role` (name unique — vi phạm → `409 ROLE_NAME_DUPLICATE`); `PATCH` sửa name/description (name trùng role khác → `409`); `DELETE` xóa row `Role` (hành vi khi role đang được gán — xem GAP-03). Mỗi mutation + audit insert nằm trong **cùng một PostgreSQL transaction** (RB-06); audit lỗi → rollback toàn bộ mutation; cache invalidation chỉ chạy sau commit.
- **Ma trận quyền — tái dùng `RbacService.replaceRolePermissions()`:** `PUT /roles/{roleId}/permissions` gọi đúng method này (đã có: khóa row role `SELECT ... FOR UPDATE` nên 2 lần thay đồng thời serialize, audit `role.permissions_updated`, role không tồn tại → `404 ROLE_NOT_FOUND`). **Không viết lại** logic thay ma trận, không tự gọi `tx.rolePermission.deleteMany/createMany` trong RolesService. `GET /roles/{roleId}/permissions` đọc ma trận hiện tại của role (join `rolePermissions` + `permissions`, trả đủ 39 code với `granted` — code nào role chưa có row thì `granted: false` hay bỏ khỏi danh sách? — xem §12 GAP-06 ghi chú: contract OpenAPI trả `permissions: [{ module, action, granted }]`; cách thể hiện code chưa được gán cần ChatGPT chốt trong GAP-06).
- **Không có DTO nào trong M02-06** (`backend/src/rbac/dto/` không tồn tại — RBAC.md §12): M06-02 tạo DTO của chính mình (`CreateRoleDto`, `UpdateRoleDto`, `UpdateRolePermissionsDto`) với `class-validator`; validation lỗi → `400 VALIDATION_ERROR` + `details: [{ field, code, message }]` (Error Catalog §2).
- **Không sửa schema/migration M02-01:** bảng `roles` đã đủ (`id`, `name` unique, `description` nullable, `createdAt`, `updatedAt`); không thêm cột/bảng. Nếu GAP-03/GAP-07 cần thêm cột (ví dụ cờ hệ thống), đó là thay đổi contract/schema — phải được ChatGPT chấp thuận trước, không tự thêm.
- **Không seed role/user:** seed permission catalog (39 code) đã có từ M02-06 (RB-08); M06-02 không tạo role mặc định, không tạo tài khoản admin mẫu (API_SECURITY §2: không có tài khoản admin mặc định sau bootstrap).

- **Lưu ý:** OpenAPI mô tả `403` của `DELETE /roles/{roleId}` gộp hai lý do ("Không có quyền roles.delete hoặc là vai trò của Super Admin cuối cùng") trong một response description, không đặt tên mã lỗi — UI và test phải phân biệt `FORBIDDEN` với `LAST_SUPER_ADMIN_ROLE` bằng trường `error` trong body, không bằng description (xem §10, G-3).

### 2.4 Phân trang, lọc, sắp xếp (API_SPEC §13)

- `GET /roles`: query `?page=<từ 1>&limit=<số item/trang>`; mặc định `page=1`, `limit=20`; `limit` tối đa 100 (vượt quá → clamp về 100, không lỗi); `page` vượt `totalPages` → trả `data: []` + `meta` đúng (không 404). Response danh sách luôn có `meta: { page, limit, total, totalPages }` (OpenAPI schema `PaginationMeta`).
- Sắp xếp: `?sort=<field>&order=asc|desc`; giá trị ngoài danh sách cho phép → `400 VALIDATION_ERROR`. Sắp xếp mặc định và tie-breaker ổn định (`id` làm khóa phụ) do Stage 2 chốt theo API_SPEC §13 — brief này không tự chốt field sắp xếp vì OpenAPI `GET /roles` không khai báo param `sort` (chỉ có `PageParam`/`LimitParam`); nếu cần sort thì đó là đề xuất thêm param, cần ChatGPT chấp thuận (xem §12, GAP-01 ghi chú).
- Không có param lọc/tìm kiếm cho `GET /roles` trong OpenAPI hiện tại — UI lọc client-side trên trang đã tải hoặc đề xuất thêm param `q` (cần chấp thuận, không tự thêm).

### 2.5 Cache + hiệu lực quyền (FR-081, BR-008, RB-04/RB-05)

- Thay đổi ma trận (`PUT /roles/{roleId}/permissions`) phải invalidate cache quyền của **mọi tài khoản mang role đó** sau commit (dùng `PermissionService.invalidateRolePermissions()` đã có — M02-06); quyền mới có hiệu lực ngay ở request tiếp theo; nếu invalidation lỗi → retry tối đa 3 lần + log/alert, không tuyên bố quyền có hiệu lực ngay khi invalidation chưa thành công; quyền cũ còn hiệu lực tối đa tới hết TTL 300 giây (RB-04).
- Tạo/sửa/xóa role (không đổi ma trận) không cần invalidate cache quyền — nhưng xóa role thì mọi tài khoản mang role đó mất quyền của role ngay khi resolve lại (resolve đọc DB; cache cũ tối đa 300 giây). Stage 2 phải invalidate cache của các tài khoản bị ảnh hưởng khi xóa role (dùng `invalidateRolePermissions` trước khi role bị xóa, hoặc invalidate theo danh sách userId lấy trước khi xóa — cách làm cụ thể do Stage 2 chốt, không đổi semantics RB-04).
- Đánh giá quyền vẫn là union role + ngoại lệ user, deny thắng allow (RB-05) — M06-02 không đổi logic resolve.

### 2.6 Audit log (FR-084, RB-06/RB-11)

- Mọi thay đổi role đều ghi 1 row `AuditLog` qua `RbacAuditService.record(tx, input)` **trong cùng transaction** với mutation (RB-06); `entityType: "ROLE"` cho cả 4 action; `actorId` lấy từ request đã xác thực (`request.admin.userId` — JwtAuthGuard); audit lỗi → rollback toàn bộ mutation.
- Payload `before`/`after` (đề xuất — CHƯA QUYẾT ĐỊNH, xem GAP-05):
  - `role.created`: `before: null`, `after: { name, description }`.
  - `role.updated`: `before: { name, description }`, `after: { name, description }` (giá trị cũ/mới đầy đủ).
  - `role.deleted`: `before: { name, description, userIds: [...], permissions: [{ module, action, granted }] }` (ghi lại những gì sẽ mất theo cascade), `after: null`.
  - `role.permissions_updated`: `before`/`after` là tập code của ma trận (do `RbacService.replaceRolePermissions` ghi sẵn — endpoint PUT không ghi audit lần 2).
- `before`/`after` chỉ chứa permission code + cờ `granted` + tên role — **không** token/mật khẩu/hash/SĐT/địa chỉ (RbacAuditService tự từ chối key cấm — AC-14 M02-06).
- Không ghi audit cho thao tác đọc (`GET /roles`, `GET /roles/{roleId}/permissions`, `GET /permissions` — tiền lệ M02-06 §2.6). Đọc audit log qua `GET /audit-logs` thuộc M06-07, không thuộc M06-02.

### 2.7 Bảo vệ Super Admin cuối cùng — KHÔNG thuộc M06-02 (RB-07)

- M06-02 **không triển khai** bất kỳ logic chặn Last-Super-Admin nào: không kiểm tra "còn lại bao nhiêu tài khoản quản trị", không định nghĩa Super Admin bằng tên role "Super Admin" hay bằng tập permission (`roles.update` + `users.update` hay bất kỳ tập quyền nào), không có code nào trong M06-02 trả `403 LAST_SUPER_ADMIN` / `403 LAST_SUPER_ADMIN_ROLE` cho tới khi GAP-02 được ChatGPT quyết.
- Yêu cầu được giữ lại cho M06-08 (tham chiếu — FR-085, BR-007, PRD §6.8, API_SECURITY §2, Error Catalog §3, API_SPEC §11.6, M02-06 §2.7): 5 thao tác bị chặn nếu khiến hệ thống không còn tài khoản quản trị nào — (a) `PUT /roles/{roleId}/permissions` bỏ quyền quản trị khỏi role của tài khoản quản trị cuối cùng; (b) `DELETE /users/{userId}/roles/{roleId}` bỏ gán role quản trị; (c) `DELETE /roles/{roleId}` xóa role của tài khoản quản trị cuối cùng; (d) `PUT /users/{userId}/permissions` đặt deny quyền quản trị; (e) tự sửa quyền của chính mình theo (a)–(d). Mã lỗi: (a)/(b)/(d)/(e) → `403 LAST_SUPER_ADMIN`; (c) → `403 LAST_SUPER_ADMIN_ROLE`.
- `RbacException` (M02-06) hiện **không có** factory `lastSuperAdmin()` / `lastSuperAdminRole()` và `RbacErrorCode` không có hai mã này (đã kiểm tra trực tiếp `backend/src/rbac/rbac.errors.ts`) — ai triển khai check (M06-08, hoặc M06-02 nếu GAP-02 quyết vậy) mới được thêm factory; M06-02 không thêm trước.
- Henry cần xác nhận định nghĩa nghiệp vụ của tài khoản Super Admin được bảo vệ trước khi M06-08 triển khai (RB-07) — brief này ghi rõ để M06-08 xin xác nhận khi tới task đó, **không hỏi Henry lúc này**.

### 2.9 Rate limit — tái dùng kind `adminAuthed` (RB-12)

- Mọi endpoint M06-02 dùng kind `adminAuthed` sẵn có: **300 lần/phút/tài khoản, fail-open** (API_SPEC §16). Không thêm kind mới. Vượt giới hạn → `429 RATE_LIMITED` + header `Retry-After`.

### 2.10 Concurrency — ETag cho PUT matrix; last-write-wins cho PATCH role

- `PUT /roles/{roleId}/permissions`: header `If-Match: <etag>` **bắt buộc** (API_SPEC §15; OpenAPI khai báo `required: true`); etag = hash của `updatedAt` + version (theo API_SPEC §15); etag không khớp → `412 PRECONDITION_FAILED`; client tải lại rồi sửa tiếp. Hai lần thay ma trận đồng thời serialize ở tầng service (row lock trong `RbacService.replaceRolePermissions` — M02-06 AC-17); trạng thái cuối bằng đúng một trong hai ma trận đầy đủ.
- `PATCH /roles/{roleId}`: last-write-wins + ghi audit log (ghi rõ ai sửa sau) — API_SPEC §15 không bắt buộc ETag cho PATCH này. Hai lần xóa/tạo trùng tên đồng thời: unique `roles.name` ở DB là chốt cuối (request thua → `409 ROLE_NAME_DUPLICATE`).
- `POST /roles` không yêu cầu `Idempotency-Key` (API_SPEC §15 chỉ bắt buộc key cho `POST /orders`, `POST /cart/items`, `POST /articles/{id}/seo/generate`) — gửi lại POST tạo role trùng tên → `409 ROLE_NAME_DUPLICATE`, không tạo role thứ hai.

### GAP-01 — Ranh giới M06-02 và M06-03: ai sở hữu ma trận quyền?

### GAP-02 — Last-Super-Admin: giữ contract DELETE/PUT chặn mà không triển khai logic M06-08 sớm — bằng cách nào?

- **Bằng chứng:** API_SPEC §11.6 + Error Catalog §3 yêu cầu `DELETE /roles/{roleId}` chặn bằng `403 LAST_SUPER_ADMIN_ROLE` và `PUT /roles/{roleId}/permissions` chặn bằng `403 LAST_SUPER_ADMIN` khi thao tác khiến Super Admin cuối cùng mất quyền quản trị. Nhưng RB-07 giao toàn bộ logic bảo vệ cho M06-08 (phụ thuộc M06-01 bootstrap/schema + Henry xác nhận định nghĩa nghiệp vụ — chưa có); `backend/src` hiện có 0 kết quả grep `LAST_SUPER_ADMIN`; `RbacException` không có factory cho hai mã này (M02-06 §2.7 liệt kê 5 thao tác bị chặn (a)–(e), trong đó (c) là xóa role).
- **Đề xuất (phương án A — khuyến nghị):** M06-02 triển khai đủ 6 endpoint **không kèm** logic chặn Last-Super-Admin; DELETE/PUT chỉ trả `FORBIDDEN` khi thiếu quyền; ghi rõ trong báo cáo Stage 2 + AC-04/AC-06 rằng hai mã `403 LAST_SUPER_ADMIN*` **chưa có hiệu lực cho tới khi M06-08** hoàn thành (M06-08 bổ sung check trong cùng transaction + hai factory lỗi). Không thêm factory lỗi speculative vào `RbacException` trong M06-02.
- **Phương án B:** M06-02 triển khai check tối thiểu ngay (đếm tài khoản quản trị còn lại trong cùng transaction — theo ràng buộc M02-06 §2.7) — nhưng việc này (1) cần định nghĩa "tài khoản quản trị" mà Henry chưa xác nhận, (2) là triển khai M06-08 sớm, trái RB-07.
- **Phương án C:** M06-02 triển khai endpoint nhưng **chưa cho go-live** DELETE/PUT-matrix cho tới khi M06-08 xong (giữ endpoint sau cờ tính năng hoặc chỉ nghiệm thu phần không liên quan Last-Super-Admin).
- **Cần ChatGPT quyết:** chọn A/B/C; nếu chọn A thì AC-04/AC-06 ghi "chưa có hiệu lực" có được chấp nhận ở nghiệm thu Stage 2 không.

### GAP-03 — Xóa role đang được tài khoản dùng: chặn, cascade thầm lặng, hay cho phép có điều kiện?

- **Bằng chứng:** Prisma schema (đọc trực tiếp): `UserRole.role` onDelete **Cascade**, `RolePermission.role` onDelete **Cascade** — xóa một `Role` thì DB tự động xóa toàn bộ `user_roles` + `role_permissions` của role đó, **không có** application-level check nào trong M02-06 (không có code xóa role). ADMIN_WIREFRAMES §11 yêu cầu: "xóa vai trò đang có tài khoản dùng → yêu cầu chuyển tài khoản trước". Error Catalog **chưa có** mã lỗi cho trường hợp này (có tiền lệ `CATEGORY_HAS_PRODUCTS`/`BRAND_HAS_PRODUCTS` 409 kèm số lượng — API_SPEC §11.6 + Catalog §5 — nhưng không có `ROLE_HAS_USERS`).
- **Đề xuất (phương án A — khuyến nghị):** chặn xóa khi role còn tài khoản dùng: trả `409 ROLE_HAS_USERS` kèm số lượng tài khoản (theo tiền lệ `CATEGORY_HAS_PRODUCTS` — message "Vai trò còn N tài khoản, cần chuyển tài khoản trước khi xóa"); cần bổ sung mã lỗi mới vào Error Catalog §5 + API_SPEC §11.6 + OpenAPI `DELETE /roles/{roleId}` (thay đổi contract — cần ChatGPT chấp thuận). UI ConfirmDialog hiển thị số tài khoản (lấy từ GAP-07).
- **Phương án B:** cho phép cascade xóa thầm lặng (đúng hành vi DB hiện tại) — trái wireframe §11; tài khoản mất quyền không báo trước; audit `before` phải ghi lại danh sách userId + ma trận bị xóa theo cascade để còn vết.
- **Phương án C:** chỉ chặn khi role là role của Super Admin cuối cùng (thuộc M06-08, thao tác (c)), còn role thường thì cascade theo B.
- **Cần ChatGPT quyết:** chọn A/B/C; nếu chọn A thì mã lỗi mới tên gì (`ROLE_HAS_USERS` hay tên khác) và message mẫu nào; nếu chọn B/C thì wireframe §11 có cần sửa câu "yêu cầu chuyển tài khoản trước" không.

### GAP-04 — Dependency M06-01: phát triển/kiểm thử M06-02 độc lập được không, vận hành thật cần gì?

M06-02 cần admin có quyền `roles.*` để thao tác — quyền này chỉ có sau khi có tài khoản + role được gán.

### GAP-05 — Audit và transaction: payload before/after cho role.created/updated/deleted

- **Bằng chứng:** RB-11 (7 action, `role.*` → entityType `ROLE`); RB-06 (audit + mutation cùng transaction, audit lỗi → rollback); `RbacAuditService.record(tx, input)` đã có (từ chối key cấm password/token/secret/hash; validate UUID/action/entityType); `RbacService.replaceRolePermissions` đã tự ghi audit `role.permissions_updated` (M06-02 không ghi lần 2 cho PUT matrix).
- **Đề xuất (payload — CHƯA QUYẾT ĐỊNH):** `role.created`: `before: null`, `after: { name, description }`. `role.updated`: `before`/`after` = `{ name, description }` đầy đủ (cũ/mới). `role.deleted`: `before: { name, description, userIds: [...], permissions: [{ module, action, granted }] }`, `after: null` — ghi lại những gì cascade sẽ xóa (phụ thuộc GAP-03: nếu chặn xóa khi còn user thì `userIds` luôn rỗng). `actorId` = `request.admin.userId` (JwtAuthGuard). Audit + mutation cùng transaction; invalidation sau commit.
- **Cần ChatGPT quyết:** chốt payload từng action (đầy đủ hay chỉ trường đổi); `before: null` hay `{}` cho create; danh sách userId trong `before` của delete có vi phạm "không ghi PII" không (userId là UUID nội bộ, không phải SĐT/địa chỉ — nhưng cần chốt).
