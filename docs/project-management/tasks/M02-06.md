## 1. Mục tiêu

Xây nền tảng phân quyền động (Dynamic RBAC, ADR-005) cho backend NestJS: permission catalog lấy đúng từ tài liệu API đã phê duyệt (không tự tạo code); đánh giá quyền bằng cách gộp quyền vai trò + ngoại lệ theo tài khoản với deny thắng allow (tái dùng logic đã nghiệm thu ở `/me` của M02-05, D-10); guard/decorator kiểm tra quyền trên mọi endpoint admin đã được bảo vệ — gọi trực tiếp API không có quyền phải nhận `403 FORBIDDEN` (FR-086); cache quyền theo ADR-006 (TTL 300 giây, invalidation khi quyền thay đổi); audit log mọi thay đổi role/permission/user-role/user-permission; seed catalog quyền idempotent từ nguồn chuẩn.

**Phạm vi M02-06 là nền tảng backend** (quyết định RB-15, §12): `PermissionsModule` + `PermissionService` độc lập, `PermissionsGuard` + decorator, cache quyền, seed catalog và audit helper — đủ tốt để các module sau tích hợp. **Không triển khai 12 endpoint quản trị RBAC** trong M02-06: Roles CRUD API + giao diện → M06-02; Permissions catalog/matrix API + giao diện → M06-03; gán role và user-permission exceptions API + giao diện → M06-04; backend enforcement coverage, kiểm tra toàn bộ endpoint admin và hardening → M06-05 (không viết lại guard); audit-log endpoint + giao diện xem log → M06-07. **Bảo vệ Super Admin cuối cùng KHÔNG thuộc M02-06** (quyết định RB-07, §12): chuyển sang M06-08, sau khi Henry xác nhận định nghĩa nghiệp vụ và M06-01 chốt bootstrap/schema — M02-06 không tự định nghĩa Super Admin bằng permission.

## 2. Phạm vi triển khai

### 2.1 Permission catalog — đầy đủ code hợp lệ từ tài liệu API; không tự tạo code mới

- Nguồn chuẩn duy nhất của catalog là **API_SPEC §6 (bảng module × quyền) + `x-required-permission` trong OpenAPI** — hai nguồn này đã được đối chiếu bằng script trong Giai đoạn 1 (xem §10): OpenAPI có 96 operation, 61 admin + 35 public, **0 operation thiếu `x-required-permission`**; 34 permission code phân biệt được endpoint dùng (không tính `*`); **không có code nào được endpoint dùng mà ngoài bảng §6**.
- Bảng §6 liệt kê **39 code** (+ `*` = đã đăng nhập). Trong đó **5 code không endpoint nào trong OpenAPI dùng** (đã xác minh bằng script, không đếm tay): `products.view`, `categories.view`, `brands.view`, `articles.view`, `fitments.update` — xem §11.2. Catalog seed lấy đúng 39 code này; **không seed code ngoài §6, không seed `*.export`** (FR-080 liệt kê Export nhưng không endpoint P0 nào dùng — RBAC Matrix §2 chú thích 2).
- **4 code `*.view` (`products.view`, `categories.view`, `brands.view`, `articles.view`) chỉ dùng cho hiển thị màn hình/admin** (quyết định RB-01, §12; RBAC Matrix §2 chú thích 1; API_SPEC §6): các `GET` danh sách/chi tiết tương ứng là public (`x-required-permission: null`) để website khách hàng đọc — guard **không** chặn các `GET` public này bằng `*.view`. 4 code này vẫn nằm trong catalog (để `/me` trả về + admin UI ẩn/hiện màn hình/sidebar theo FR-077/FR-081 + `GET /permissions` liệt kê đủ ma trận).
- **`fitments.update` được seed vào catalog dù không endpoint nào dùng** (quyết định RB-02, §12 — chọn phương án A): API_SPEC §6 liệt kê `fitments.view/create/update/delete`, nhưng không endpoint nào trong OpenAPI dùng `fitments.update`; RBAC Matrix §2 chú thích 3 ghi rõ module Fitment không có Update (sửa fitment = xóa + gắn lại). Seed code này để catalog khớp §6 hoàn toàn; code tồn tại trong DB + `/me` + `GET /permissions` nhưng **không guard nào yêu cầu nó** (tương tự 4 code `*.view`) — **đây là permission chưa có endpoint sử dụng; không tự tạo endpoint hoặc hành vi mới cho nó**.
- **Không hard-code 5 vai trò ví dụ trong RBAC Matrix thành danh sách vai trò cố định** (RBAC Matrix §1/§3, PRD mục 3): catalog chỉ seed **permission**, không seed role nào. Vai trò thật do Super Admin tạo qua API (`POST /roles`, M06-02) — M02-06 không tạo role mẫu, không tạo tài khoản admin mẫu.
- `GET /permissions` (Admin, `roles.view`) trả toàn bộ catalog theo module — dùng để render ma trận checkbox (FR-080). Response lấy từ bảng `permissions` trong DB (đã seed), không hard-code danh sách trong code.

### 2.2 Permission evaluation — gộp quyền vai trò + ngoại lệ; deny thắng allow

- **Tái dùng logic đã nghiệm thu ở M02-05 (D-10):** `AuthService.getMe()` (`backend/src/auth/auth.service.ts`, đã đọc trực tiếp trong Giai đoạn 1) là nơi duy nhất hiện resolve permission trong code — đọc `userRoles → role → rolePermissions` + `userPermissions`, gộp vào hai tập `allows`/`denies` (cả `granted = false` ở cấp role lẫn cấp user đều vào `denies`), kết quả cuối = `allows` trừ `denies`, sắp xếp. **M02-06 tách logic này thành `PermissionService` trong `PermissionsModule` độc lập** (quyết định RB-13, §12) để cả `/me` và guard dùng **cùng một hàm duy nhất**; `/me` sau khi tách phải trả kết quả giống hệt G4 của M02-05 (AC-13).
- **Semantics đã quyết định (RB-05, §12): deny luôn thắng allow.** Bất kỳ `granted = false` nào (ở `role_permissions` hay `user_permissions`) cũng loại code đó khỏi tập quyền cuối — đúng hành vi hiện tại của `getMe` (đã nghiệm thu G4). Áp dụng cho mọi cặp xung đột:
  - Role A grant + role B deny cùng code → **deny**.
  - Role grant + user deny cùng code → **deny**.
  - User grant + role deny cùng code → **deny** (tài khoản không tự grant lại được quyền mà role đã deny).
  - User grant + user deny cùng code → **không thể cùng tồn tại** do khóa duy nhất `(userId, permissionId)` trên `user_permissions`.
  Guard và `/me` dùng cùng một hàm resolve duy nhất, giữ nguyên semantics này.
- **Access token không chứa permission list** (API_SPEC §5: access claims chỉ `sub`/`roles`/`type`/`sid`/`iat`/`exp`) — guard **không bao giờ** tin quyền đọc từ token; guard resolve lại từ DB/cache mỗi request (xem §2.5). Role ids trong token chỉ dùng để biết tài khoản thuộc vai trò nào khi cần ghi log, không dùng để quyết định quyền.
- **Tài khoản mới mặc định không có quyền gì** (API_SECURITY §2, least privilege): user chưa được gán role nào và chưa có ngoại lệ → tập quyền rỗng → mọi endpoint admin (trừ `*`) đều 403. Không có role mặc định, không có quyền mặc định.
- **Thứ tự ưu tiên giữa role grant và user-level deny đã quyết định theo RB-05 (§12):** deny thắng allow trong mọi cặp xung đột liệt kê ở trên — đúng semantics của `getMe` đã nghiệm thu, không đổi hành vi.

### 2.3 NestJS authorization guard/decorator — backend kiểm tra quyền trên mọi endpoint được bảo vệ

- **Cơ chế đã quyết định (RB-09, §12): NestJS Guard + decorator, không dùng Express middleware.** `PermissionsGuard` (NestJS `CanActivate`) + decorator `@RequirePermission("<module>.<action>")` đặt trên controller/handler; guard chạy **sau** `JwtAuthGuard` (xác thực trước, phân quyền sau). Guard đọc permission yêu cầu từ metadata của decorator; đối chiếu với tập quyền đã resolve của tài khoản (xem §2.2/§2.5); thiếu quyền → `403 FORBIDDEN` (Error Catalog §3), không lộ thêm thông tin. Guard được gắn **rõ ràng cho controller/route admin, không áp dụng global** theo cách có thể vô tình chặn endpoint public. Không cần `@RequireAnyPermission` (mọi operation chỉ có một code) — nếu một task sau phát hiện operation cần nhiều code thì xin quyết định riêng, không tự thêm decorator.
- **Phạm vi áp dụng:** toàn bộ **61 operation admin** có `x-required-permission` khác `null` trong OpenAPI (đã liệt kê đủ ở §11.2) — bao gồm cả 12 endpoint quản trị RBAC (§2.9, thuộc M06-02/03/04/07). **35 operation public** (`x-required-permission: null`) không qua guard. **2 endpoint `*`** (`POST /auth/admin/logout`, `GET /auth/admin/me`) chỉ cần đã đăng nhập — guard bỏ qua kiểm tra permission khi code là `*` (đã xác thực bởi `JwtAuthGuard`). **Phân chia theo RB-15 (§12):** M02-06 xây guard + decorator nền tảng và kiểm thử trên test controller trong spec e2e (§7); việc gắn guard lên từng endpoint admin của từng module diễn ra khi task của module đó triển khai endpoint — **M06-05 chịu trách nhiệm tích hợp, rà soát coverage toàn bộ 61 operation và hardening enforcement, không viết lại một bộ guard thứ hai**. M02-06 không tự triển khai decorator cho 61 operation chưa có controller.
- **Ánh xạ decorator ↔ OpenAPI là 1:1 theo `x-required-permission`:** mỗi operation admin mang đúng một code (hoặc `*`); không operation nào mang nhiều code; không tự thêm code cho operation nào. Quy tắc ánh xạ này là chuẩn cho mọi module khi gắn decorator; kiểm tra bằng script đối chiếu (decorator trong code khớp `x-required-permission` trong OpenAPI cho mọi operation) thuộc **M06-05** (AC-02).
- **Thứ tự kiểm tra trong một request (theo JwtAuthGuard M02-05 + guard mới):** (1) verify chữ ký + thời hạn + `type: "access"` của JWT; (2) kiểm tra blacklist Redis (fail-closed 503 — M02-05 D-06, AC-18); (3) kiểm tra trạng thái session theo `sid`; (4) rate limit `adminAuthed` (fail-open theo rule hiện có); (5) resolve permission (cache → DB) + kiểm tra code yêu cầu → thiếu quyền 403. Không đảo thứ tự (không kiểm tra permission trước khi biết tài khoản là ai).
- **`GET /admin/dashboard/summary` (Admin, `dashboard.view`) là ngoại lệ hiển thị từng phần (FR-077, API_SPEC §11.6):** guard chỉ kiểm tra `dashboard.view`; việc ẩn từng số liệu theo quyền khác (`orders.view` → `pendingOrders` trả `null` + `hiddenByPermission: true`) là logic của handler dashboard, **không thuộc M02-06** — ghi rõ để không nhầm guard 403 cả endpoint khi tài khoản thiếu `orders.view`.

### 2.4 Tích hợp Auth M02-05 — lấy danh tính và session từ access token đã xác thực; không tự viết lại authentication

- M02-06 **không viết lại authentication**: tái dùng `JwtAuthGuard` (đã nghiệm thu G4) để xác thực; `PermissionsGuard` chỉ nhận `request.admin` (`userId`, `sessionId`, `roles`, `accessToken`, `accessTokenExp`) do `JwtAuthGuard` gắn vào request. Không sửa `JwtAuthGuard`, `TokenService`, `AuthService.login/refresh/logout` trong task này (ranh giới — xem §4; nếu phát hiện cần sửa Auth thì dừng và xin phê duyệt riêng).
- **Không sửa claims của access token** (API_SPEC §5): không thêm permission list vào JWT; không đổi TTL 15 phút; không đổi `sid`. Việc resolve quyền mỗi request qua cache (TTL 300 giây) là thiết kế đã chốt ở ADR-006 — không dùng token làm cache quyền.
- **Tài khoản `isActive = false` hoặc session đã thu hồi:** đã bị `JwtAuthGuard` chặn trước khi tới guard quyền (401) — guard quyền không cần kiểm tra lại trạng thái tài khoản/session.
- **Rate limit cho endpoint RBAC (quyết định RB-12, §12):** dùng kind `adminAuthed` sẵn có (300 lần/phút/tài khoản, fail-open — M02-02) cho mọi endpoint admin đã đăng nhập, bao gồm các endpoint RBAC (§2.9); **không thêm kind mới trong M02-06**.
- **Tách module theo RB-13 (§12):** `PermissionService` nằm trong `PermissionsModule` độc lập — module này **không phụ thuộc `AuthModule`**; `AuthModule` và `RbacModule` **cùng import** `PermissionsModule`. `AuthService.getMe()` gọi `PermissionService` (giữ nguyên response — AC-13); `RbacModule` dùng cùng service cho guard. `RbacModule` có thể import `AuthModule` để tái sử dụng `JwtAuthGuard`. **Không tạo circular dependency** (`AuthModule` → `PermissionsModule`, `RbacModule` → `PermissionsModule` + `AuthModule`; `PermissionsModule` không import ngược lại).

### 2.5 Permission cache — tuân thủ ADR-006, TTL 300 giây và invalidation khi quyền thay đổi

- **TTL 300 giây (đã xác minh bằng code, không phải số bịa):** `CACHE_TTL_SECONDS.userPermissions = 300` trong `packages/shared/src/index.ts` (có unit test assert đúng 300); `resolveCacheTtl("userPermissions")` trong `backend/src/redis/cache-ttl.config.ts` trả đúng giá trị này. M02-06 dùng đúng kind `userPermissions` này — không hard-code số 300 trong code nghiệp vụ.
- **Key scheme (M02-02, đã có sẵn):** `buildCacheKey(module, entity, id)` → `seecarauto:v1:<module>:<entity>:<id>`; đề xuất key quyền theo tài khoản `seecarauto:v1:rbac:permissions:<userId>` (module `rbac`, entity `permissions`) — giá trị cache là danh sách code đã resolve (mảng string đã sắp xếp, đúng định dạng `/me` trả về). **Không cache token/secret/hash/mật khẩu** (ADR-006: không cache thông tin nhạy cảm); danh sách permission code không phải secret.
- **Cache-aside qua `CacheService` (M02-02):** `get` → miss → resolve từ DB → `set` với TTL 300 → trả. Dùng `remember` + lock chống stampede đã có sẵn trong `CacheService` khi nhiều request cùng miss một user.
- **Invalidation (FR-081, BR-008):** mọi thay đổi quyền (PUT role permissions, PUT user permissions, gán/bỏ gán role, xóa role) phải invalidate cache quyền của **mọi tài khoản bị ảnh hưởng** (tất cả user mang role đó + user đích của ngoại lệ) — dùng `CacheService.deleteByPattern`/`invalidateModule` với prefix `seecarauto:v1:rbac:` hoặc xóa từng key user (cơ chế cụ thể do Stage 2 chốt; không quét toàn bộ keyspace bằng `KEYS`). Invalidation chạy **sau khi DB transaction commit** (không nằm trong transaction — Redis không tham gia transaction PostgreSQL); thứ tự commit → invalidate là bắt buộc (xem RB-06).
- **Trường hợp cache lỗi / Redis lỗi / invalidation lỗi (quyết định RB-04, §12):**
  - **Guard fallback DB khi Redis lỗi:** không được từ chối request hợp lệ chỉ vì cache Redis lỗi nếu DB vẫn truy cập được — guard đọc thẳng DB để resolve quyền (đúng kết quả, chậm hơn, vẫn phục vụ request). Khác với blacklist (M02-05 D-06/AC-18): sai sót ở đây chỉ làm chậm, không làm token đã thu hồi sống lại vì blacklist/session vẫn do `JwtAuthGuard` kiểm tra riêng.
  - **Invalidation lỗi:** retry **tối đa 3 lần**, ghi log/alert nếu thất bại; **không được tuyên bố quyền đã có hiệu lực ngay khi invalidation chưa thành công**. Quyền cũ còn hiệu lực tối đa tới hết TTL 300 giây — TTL là chặn trên của độ trễ (FR-081 cho phép trễ tới khi invalidate).
  - **Phân biệt hai tình huống trong kiểm thử (AC-06):** DB fallback (cache lỗi nhưng DB trả đúng quyền mới) khác với quyền cũ còn trong cache (invalidation chưa thành công — request sau thay đổi có thể thấy quyền cũ tới hết TTL). Không nhầm hai trường hợp này với nhau.
- **Không dùng cache làm nguồn đúng cho trạng thái thu hồi:** cache chỉ lưu tập quyền đã resolve; trạng thái session/blacklist vẫn do `JwtAuthGuard` kiểm tra trực tiếp (Redis blacklist + DB session) — cache quyền hết hạn/sai không làm token đã logout sống lại.

### 2.6 Audit log — ghi nhận thay đổi role, permission, user-role và user-permission; không ghi token/secret/dữ liệu nhạy cảm

- **Phạm vi audit (FR-084, API_SPEC §18):** mọi thay đổi quyền đều ghi `AuditLog`: tạo/sửa/xóa role; cập nhật ma trận quyền của role (`PUT /roles/{roleId}/permissions`); gán/bỏ gán role cho tài khoản; cập nhật ngoại lệ quyền theo tài khoản (`PUT /users/{userId}/permissions`). Các endpoint thực hiện thay đổi này thuộc M06-02/03/04 (§2.9) — **M02-06 cung cấp helper ghi audit dùng chung để các endpoint đó gọi**; M02-06 không triển khai endpoint quản trị RBAC. Mỗi row ghi đủ `actorId` (admin thực hiện), `action`, `entityType`, `entityId`, `before`, `after` (JSON — chỉ chứa permission code + cờ `granted` + tên role, **không** token/mật khẩu/hash/SĐT/địa chỉ), `createdAt` (theo schema `AuditLog` đã có — `actorId` bắt buộc + FK tới `User` Restrict, `entityId` nullable UUID).
- **Tên action (quyết định RB-11, §12):** dùng dạng `<entity>.<verb>` thống nhất cho 7 sự kiện RBAC: `role.created`, `role.updated`, `role.deleted`, `role.permissions_updated`, `user.roles_assigned`, `user.roles_removed`, `user.permissions_updated`. **`entityType`:** dùng `ROLE` cho thay đổi role/role permissions và `USER` cho thay đổi gán quyền theo tài khoản. Helper audit thiết kế dùng chung; M02-06 cung cấp nền tảng, các task module sau tái sử dụng.
- **Transaction và audit (quyết định RB-06, §12):** audit insert nằm **trong cùng một PostgreSQL transaction** với thao tác thay đổi quyền (theo tiền lệ M02-05 FIX-08: audit lockout/reuse/revoke-all trong cùng transaction) — thay đổi quyền thất bại/rollback thì **không được để audit ghi nhận một thay đổi chưa commit**; audit insert lỗi → rollback toàn bộ thao tác. Cache invalidation chạy sau commit (xem §2.5), không nằm trong transaction.
- **`GET /audit-logs` (Admin, `audit.view`) thuộc M06-07 (§2.9):** đọc audit theo filter `actorId?`, `entityType?`, `entityId?`, `from?`, `to?` + phân trang (API_SPEC §11.6); response `{ id, actorId, action, entityType, entityId, before, after, createdAt }`. M02-06 không triển khai endpoint này — audit cho thay đổi trạng thái đơn (FR-066) / fitment (FR-033) / sản phẩm thuộc task của các module đó, tái dùng helper ghi audit của M02-06 (xem RB-11).

### 2.7 Bảo vệ Super Admin cuối cùng — KHÔNG thuộc M02-06, chuyển sang M06-08

- **Quyết định RB-07 (§12): CHƯA cho triển khai trong M02-06.** Việc xác định và bảo vệ Super Admin cuối cùng chuyển sang **M06-08**, phụ thuộc quyết định bootstrap/schema của M06-01. - **Không được tự định nghĩa Super Admin bằng hai permission `roles.update` và `users.update`:** người có hai quyền này chưa chắc là tài khoản Super Admin được bảo vệ. M02-06 không dùng định nghĩa này làm thay thế, không hard-code nó ở bất kỳ đâu.
- **Henry cần xác nhận định nghĩa nghiệp vụ trước khi M06-08 triển khai** — đây là quyết định của Henry trong tương lai; brief ghi rõ để M06-08 xin xác nhận khi tới task đó, **không hỏi Henry lúc này**.
- **Yêu cầu được giữ lại cho M06-08 (tham chiếu — FR-085, BR-007, PRD §6.8, API_SECURITY §2, Error Catalog §3, API_SPEC §11.6):** mọi thao tác dưới đây, nếu khiến hệ thống không còn tài khoản quản trị nào, đều bị chặn kèm thông báo rõ — **không có ngoại lệ**:
  - (a) `PUT /roles/{roleId}/permissions` bỏ quyền quản trị khỏi role mà tài khoản quản trị cuối cùng đang mang;
  - (b) `DELETE /users/{userId}/roles/{roleId}` bỏ gán role quản trị khỏi tài khoản quản trị cuối cùng;
  - (c) `DELETE /roles/{roleId}` xóa role mà tài khoản quản trị cuối cùng đang mang (và không còn role quản trị nào khác);
  - (d) `PUT /users/{userId}/permissions` đặt ngoại lệ deny (`granted = false`) cho quyền quản trị của tài khoản quản trị cuối cùng;
  - (e) tự sửa quyền của chính mình theo (a)–(d) (PRD §6.8: thay đổi quyền của chính mình yêu cầu xác nhận + ghi audit — xem RB-10; xác nhận không thay thế việc chặn: nếu thao tác vi phạm quy tắc cuối cùng thì vẫn chặn dù đã xác nhận).
- **Mã lỗi (theo Error Catalog §3 + API_SPEC §11.6, dùng ở M06-08):** thao tác (a)/(b)/(d)/(e) → `403 LAST_SUPER_ADMIN`; thao tác (c) xóa role → `403 LAST_SUPER_ADMIN_ROLE`. Message tiếng Việt theo Catalog; không lộ thêm thông tin. Các mã lỗi này vẫn nằm trong Error Catalog (đã có từ M01-03) để M06-08 dùng — M02-06 không xóa chúng khỏi Catalog.
- **Ràng buộc cho M06-08 (ghi để task sau dùng, không triển khai ở M02-06):** schema `User`/`Role` không có cột cờ Super Admin; 5 vai trò ví dụ không được hard-code nên không được định nghĩa Super Admin bằng tên role "Super Admin". Mọi thao tác (a)–(e) phải kiểm tra định nghĩa đã chốt **trong cùng transaction** với thao tác (đếm số tài khoản quản trị còn lại sau khi áp dụng thay đổi; nếu còn 0 → chặn) để hai request đồng thời không cùng bỏ quyền của hai tài khoản quản trị cuối cùng. Không đếm bằng cache (cache có thể cũ); không đếm bằng token claims.

### 2.8 Seed/catalog dữ liệu quyền — nguồn dữ liệu chuẩn, tính idempotent, cách xử lý permission đã tồn tại

- **Nguồn chuẩn:** API_SPEC §6 (39 code) + OpenAPI `x-required-permission` (đối chiếu §10/§11.2); seed lấy danh sách code từ hai nguồn này — **không lấy từ RBAC Matrix** (matrix là tài liệu UI/UX, có 3 điểm lệch đã ghi ở §10: claim §7 sai với 5 code, gap bảng đã cũ, trích dẫn PRD §6.7 sai).
- **Cơ chế seed (quyết định RB-08, §12):** script seed riêng `backend/prisma/seed-permissions.ts` (chạy bằng `prisma db seed` hoặc `pnpm exec tsx` — lệnh chạy cụ thể do Stage 2 chốt), dùng `upsert` theo unique `(module, action)`: code chưa có → insert (module, action, description); code đã có → **giữ nguyên, không ghi đè description** (description có thể đã được admin sửa tay); code trong DB mà không có trong catalog chuẩn → **không xóa, chỉ báo cáo** (log danh sách để ChatGPT/M06 xử lý — xóa permission đang được role/user tham chiếu sẽ phá dữ liệu). Description mặc định của code mới: lấy đúng mô tả trong API_SPEC §6 nếu có; nếu §6 không có mô tả thì để null (không tự bịa description).
- **Tính idempotent:** chạy seed nhiều lần cho kết quả cuối giống hệt nhau (đúng N row, không duplicate — unique `(module, action)` bảo đảm ở DB); seed không tạo role, không gán quyền cho ai, không tạo tài khoản.
- **Hiện trạng đã xác minh:** repo **chưa có file seed nào** (`find *seed*` trong repo không trả kết quả; `backend/prisma/` chỉ có `migrations/` + `schema.prisma`) — seed là file mới hoàn toàn, không sửa seed cũ.
- **Khi seed chạy (quyết định RB-08, §12):** chạy **tường minh trong quy trình triển khai, sau migration và trước khi đưa chức năng phụ thuộc vào hoạt động**; **không** chạy seed trong request path; **không** tự động chạy mỗi lần app boot. **Cho phép chạy lại ở production có kiểm soát** (seed idempotent nên chạy lại an toàn).

- **Deny thắng allow (quyết định RB-05, §12):** mọi `granted = false` (cấp role hay cấp user) đều loại code khỏi tập quyền cuối — role A grant + role B deny → deny; role grant + user deny → deny; user grant + role deny → deny; user grant + user deny không thể cùng tồn tại do khóa duy nhất. ## 7. Kế hoạch kiểm thử

- **Unit** (`permission.service.spec.ts`, `permissions.guard.spec.ts`): ma trận đánh giá quyền — role grant + role deny + user grant + user deny + nhiều role xung đột (deny thắng mọi trường hợp, đúng RB-05); resolve rỗng khi user không có role; TTL resolve `userPermissions` = 300; key cache đúng scheme `seecarauto:v1:rbac:permissions:<userId>`; guard trả 403 khi thiếu code, cho qua khi đủ code, bỏ qua khi code là `*`; helper audit ghi đúng action/entityType khi actor tự sửa quyền của chính mình (RB-10/RB-11). Mock Prisma/Redis ở mức service boundary, giữ nguyên logic nghiệp vụ.
- **Integration** (guard trên controller test + CacheService thật với Redis test port 6399): guard + JwtAuthGuard xếp chồng đúng thứ tự (chưa đăng nhập → 401, đã đăng nhập thiếu quyền → 403); cache hit/miss/invalidate với Redis thật; stampede (nhiều request cùng miss một user → chỉ 1 lần resolve DB); Redis lỗi → guard fallback đọc DB (RB-04).
- **E2E** (`backend/test/rbac.e2e-spec.ts`): PostgreSQL test thật + Redis test port 6399 (mẫu M02-02/M02-03/M02-05) + JWT secret test. User/role/permission test tạo trực tiếp bằng Prisma (Argon2id hash thật cho user; role + permission tạo qua seed + ghi trực tiếp DB trong setup test — không qua API M06). Guard kiểm thử trên **test controller** trong spec (gắn `@RequirePermission` cho từng loại code — test controller chỉ tồn tại trong spec, không phải endpoint sản phẩm). Kịch bản: AC-01 → AC-18 trong phạm vi M02-06 (catalog, 403 trực tiếp qua test controller, 4 code `*.view`, cache TTL/invalidate, Redis lỗi + invalidation lỗi theo RB-04, audit + rollback, seed idempotent, ma trận lỗi ở tầng service, `/me` không đổi, rate limit, đồng thời thay đổi ma trận ở tầng service).

### RB-05 — Deny luôn thắng allow — ĐÃ QUYẾT ĐỊNH

- **Quyết định: deny luôn thắng allow.**
  - Role A grant + role B deny cùng code → deny.
  - Role grant + user deny cùng code → deny.
  - User grant + role deny cùng code → deny.
  - User grant + user deny cùng code → không thể cùng tồn tại do khóa duy nhất `(userId, permissionId)`.
- Giữ nguyên semantics `/me` của M02-05.
- Áp dụng: §2.2, §3, AC-03.
