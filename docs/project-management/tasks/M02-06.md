## 1. Mục tiêu

Xây nền tảng phân quyền động (Dynamic RBAC, ADR-005) cho backend NestJS: permission catalog lấy đúng từ tài liệu API đã phê duyệt (không tự tạo code); đánh giá quyền bằng cách gộp quyền vai trò + ngoại lệ theo tài khoản với deny thắng allow (tái dùng logic đã nghiệm thu ở `/me` của M02-05, D-10); guard/decorator kiểm tra quyền trên mọi endpoint admin đã được bảo vệ — gọi trực tiếp API không có quyền phải nhận `403 FORBIDDEN` (FR-086); cache quyền theo ADR-006 (TTL 300 giây, invalidation khi quyền thay đổi); audit log mọi thay đổi role/permission/user-role/user-permission; chặn mọi thao tác khiến hệ thống mất tài khoản quản trị cuối cùng (FR-085, BR-007); seed catalog quyền idempotent từ nguồn chuẩn.

**Giai đoạn 1 (brief này) chỉ chuẩn bị:** đọc tài liệu, đối chiếu RBAC Matrix với API_SPEC/OpenAPI bằng script, kiểm tra Prisma schema trực tiếp, tạo Task Brief với AC kiểm chứng được, bảng đối chiếu, điểm chưa quyết định, test strategy, danh sách file dự kiến. **Chưa triển khai code.** Báo cáo ChatGPT review rồi mới nhận lệnh triển khai.

## 2. Phạm vi triển khai

### 2.1 Permission catalog — đầy đủ code hợp lệ từ tài liệu API; không tự tạo code mới

- Nguồn chuẩn duy nhất của catalog là **API_SPEC §6 (bảng module × quyền) + `x-required-permission` trong OpenAPI** — hai nguồn này đã được đối chiếu bằng script trong Giai đoạn 1 (xem §10): OpenAPI có 96 operation, 61 admin + 35 public, **0 operation thiếu `x-required-permission`**; 34 permission code phân biệt được endpoint dùng (không tính `*`); **không có code nào được endpoint dùng mà ngoài bảng §6**.
- Bảng §6 liệt kê **39 code** (+ `*` = đã đăng nhập). Trong đó **5 code không endpoint nào trong OpenAPI dùng** (đã xác minh bằng script, không đếm tay): `products.view`, `categories.view`, `brands.view`, `articles.view`, `fitments.update` — xem §11.2. Catalog seed lấy đúng 39 code này (trừ khi ChatGPT quyết khác ở RB-02 đối với `fitments.update`); **không seed code ngoài §6, không seed `*.export`** (FR-080 liệt kê Export nhưng không endpoint P0 nào dùng — RBAC Matrix §2 chú thích 2).
- **4 code `*.view` (`products.view`, `categories.view`, `brands.view`, `articles.view`) chỉ dùng cho hiển thị màn hình/admin** (RBAC Matrix §2 chú thích 1; API_SPEC §6): các `GET` danh sách/chi tiết tương ứng là public (`x-required-permission: null`) để website khách hàng đọc — guard **không** chặn các `GET` public này bằng `*.view`. 4 code này vẫn nằm trong catalog (để `/me` trả về + admin UI ẩn/hiện màn hình/sidebar theo FR-077/FR-081 + `GET /permissions` liệt kê đủ ma trận) — xem RB-01.
- **`fitments.update` là mâu thuẫn tài liệu chưa giải quyết** (RB-02): API_SPEC §6 liệt kê `fitments.view/create/update/delete`, nhưng không endpoint nào trong OpenAPI dùng `fitments.update`; RBAC Matrix §2 chú thích 3 ghi rõ module Fitment không có Update (sửa fitment = xóa + gắn lại). Brief này **không tự quyết** code này có được seed hay không — chờ ChatGPT (RB-02).
- **Không hard-code 5 vai trò ví dụ trong RBAC Matrix thành danh sách vai trò cố định** (RBAC Matrix §1/§3, PRD mục 3): catalog chỉ seed **permission**, không seed role nào. Vai trò thật do Super Admin tạo qua API (`POST /roles`, M06-02) — M02-06 không tạo role mẫu, không tạo tài khoản admin mẫu.
- `GET /permissions` (Admin, `roles.view`) trả toàn bộ catalog theo module — dùng để render ma trận checkbox (FR-080). Response lấy từ bảng `permissions` trong DB (đã seed), không hard-code danh sách trong code.

### 2.2 Permission evaluation — gộp quyền vai trò + ngoại lệ; deny thắng allow

- **Tái dùng logic đã nghiệm thu ở M02-05 (D-10):** `AuthService.getMe()` (`backend/src/auth/auth.service.ts`, đã đọc trực tiếp trong Giai đoạn 1) là nơi duy nhất hiện resolve permission trong code — đọc `userRoles → role → rolePermissions` + `userPermissions`, gộp vào hai tập `allows`/`denies` (cả `granted = false` ở cấp role lẫn cấp user đều vào `denies`), kết quả cuối = `allows` trừ `denies`, sắp xếp. **M02-06 tách logic này thành hàm dùng chung** (đề xuất: `PermissionService.resolvePermissions(userId)` — xem RB-13 về vị trí đặt hàm) để cả `/me` và guard dùng **cùng một hàm duy nhất**; `/me` sau khi tách phải trả kết quả giống hệt G4 của M02-05 (AC-13).
- **Semantics đề xuất (chờ ChatGPT chốt — RB-05):** deny thắng allow ở mọi cấp — bất kỳ `granted = false` nào (ở `role_permissions` hay `user_permissions`) cũng loại code đó khỏi tập quyền cuối, kể cả khi một role khác grant hoặc ngoại lệ user grant cùng code. Đây đúng là hành vi hiện tại của `getMe` (đã nghiệm thu G4) — brief chỉ yêu cầu ChatGPT xác nhận semantics này là semantics cuối cho guard, không tự chốt thêm trường hợp ưu tiên nào khác.
- **Access token không chứa permission list** (API_SPEC §5: access claims chỉ `sub`/`roles`/`type`/`sid`/`iat`/`exp`) — guard **không bao giờ** tin quyền đọc từ token; guard resolve lại từ DB/cache mỗi request (xem §2.5). Role ids trong token chỉ dùng để biết tài khoản thuộc vai trò nào khi cần ghi log, không dùng để quyết định quyền.
- **Tài khoản mới mặc định không có quyền gì** (API_SECURITY §2, least privilege): user chưa được gán role nào và chưa có ngoại lệ → tập quyền rỗng → mọi endpoint admin (trừ `*`) đều 403. Không có role mặc định, không có quyền mặc định.
- **Thứ tự ưu tiên giữa role grant và user-level deny** là điểm phải làm rõ (ChatGPT §4 — RB-05): đề xuất deny thắng allow như trên; trường hợp role A grant + role B deny cùng code, và trường hợp user-level grant + role-level deny, đều theo cùng quy tắc deny thắng — cần ChatGPT xác nhận tường minh vì API_SECURITY §2 chỉ ghi "deny lấn át allow" mà chưa liệt kê hết các cặp xung đột.

### 2.3 NestJS authorization guard/decorator — backend kiểm tra quyền trên mọi endpoint được bảo vệ

- **Đề xuất (chờ ChatGPT chốt cơ chế — RB-09):** `PermissionsGuard` (NestJS `CanActivate`) + decorator `@RequirePermission("<module>.<action>")` đặt trên controller/handler; guard chạy **sau** `JwtAuthGuard` (xác thực trước, phân quyền sau). Guard đọc permission yêu cầu từ metadata của decorator; đối chiếu với tập quyền đã resolve của tài khoản (xem §2.2/§2.5); thiếu quyền → `403 FORBIDDEN` (Error Catalog §3), không lộ thêm thông tin.
- **Phạm vi áp dụng:** toàn bộ **61 operation admin** có `x-required-permission` khác `null` trong OpenAPI (đã liệt kê đủ ở §11.2) — bao gồm cả 13 endpoint quản trị RBAC (§2.9). **35 operation public** (`x-required-permission: null`) không qua guard. **2 endpoint `*`** (`POST /auth/admin/logout`, `GET /auth/admin/me`) chỉ cần đã đăng nhập — guard bỏ qua kiểm tra permission khi code là `*` (đã xác thực bởi `JwtAuthGuard`).
- **Ánh xạ decorator ↔ OpenAPI là 1:1 theo `x-required-permission`:** mỗi operation admin mang đúng một code (hoặc `*`); không operation nào mang nhiều code; không tự thêm code cho operation nào. Test kiểm tra ánh xạ này bằng script đối chiếu (AC-02): decorator trong code khớp `x-required-permission` trong OpenAPI cho mọi operation.
- **Thứ tự kiểm tra trong một request (theo JwtAuthGuard M02-05 + guard mới):** (1) verify chữ ký + thời hạn + `type: "access"` của JWT; (2) kiểm tra blacklist Redis (fail-closed 503 — M02-05 D-06, AC-18); (3) kiểm tra trạng thái session theo `sid`; (4) rate limit `adminAuthed` (fail-open theo rule hiện có); (5) resolve permission (cache → DB) + kiểm tra code yêu cầu → thiếu quyền 403. Không đảo thứ tự (không kiểm tra permission trước khi biết tài khoản là ai).
- **`GET /admin/dashboard/summary` (Admin, `dashboard.view`) là ngoại lệ hiển thị từng phần (FR-077, API_SPEC §11.6):** guard chỉ kiểm tra `dashboard.view`; việc ẩn từng số liệu theo quyền khác (`orders.view` → `pendingOrders` trả `null` + `hiddenByPermission: true`) là logic của handler dashboard, **không thuộc M02-06** — ghi rõ để không nhầm guard 403 cả endpoint khi tài khoản thiếu `orders.view`.

### 2.4 Tích hợp Auth M02-05 — lấy danh tính và session từ access token đã xác thực; không tự viết lại authentication

- M02-06 **không viết lại authentication**: tái dùng `JwtAuthGuard` (đã nghiệm thu G4) để xác thực; `PermissionsGuard` chỉ nhận `request.admin` (`userId`, `sessionId`, `roles`, `accessToken`, `accessTokenExp`) do `JwtAuthGuard` gắn vào request. Không sửa `JwtAuthGuard`, `TokenService`, `AuthService.login/refresh/logout` trong task này (ranh giới — xem §4; nếu phát hiện cần sửa Auth thì dừng và xin phê duyệt riêng).
- **Không sửa claims của access token** (API_SPEC §5): không thêm permission list vào JWT; không đổi TTL 15 phút; không đổi `sid`. Việc resolve quyền mỗi request qua cache (TTL 300 giây) là thiết kế đã chốt ở ADR-006 — không dùng token làm cache quyền.
- **Tài khoản `isActive = false` hoặc session đã thu hồi:** đã bị `JwtAuthGuard` chặn trước khi tới guard quyền (401) — guard quyền không cần kiểm tra lại trạng thái tài khoản/session.
- **Rate limit cho endpoint RBAC:** dùng kind `adminAuthed` sẵn có (300 lần/phút/tài khoản, fail-open — M02-02) cho mọi endpoint admin đã đăng nhập, bao gồm các endpoint RBAC (§2.9); không thêm kind mới trừ khi ChatGPT quyết khác (RB-12).

### 2.5 Permission cache — tuân thủ ADR-006, TTL 300 giây và invalidation khi quyền thay đổi

- **TTL 300 giây (đã xác minh bằng code, không phải số bịa):** `CACHE_TTL_SECONDS.userPermissions = 300` trong `packages/shared/src/index.ts` (có unit test assert đúng 300); `resolveCacheTtl("userPermissions")` trong `backend/src/redis/cache-ttl.config.ts` trả đúng giá trị này. M02-06 dùng đúng kind `userPermissions` này — không hard-code số 300 trong code nghiệp vụ.
- **Key scheme (M02-02, đã có sẵn):** `buildCacheKey(module, entity, id)` → `seecarauto:v1:<module>:<entity>:<id>`; đề xuất key quyền theo tài khoản `seecarauto:v1:rbac:permissions:<userId>` (module `rbac`, entity `permissions`) — giá trị cache là danh sách code đã resolve (mảng string đã sắp xếp, đúng định dạng `/me` trả về). **Không cache token/secret/hash/mật khẩu** (ADR-006: không cache thông tin nhạy cảm); danh sách permission code không phải secret.
- **Cache-aside qua `CacheService` (M02-02):** `get` → miss → resolve từ DB → `set` với TTL 300 → trả. Dùng `remember` + lock chống stampede đã có sẵn trong `CacheService` khi nhiều request cùng miss một user.
- **Invalidation (FR-081, BR-008):** mọi thay đổi quyền (PUT role permissions, PUT user permissions, gán/bỏ gán role, xóa role) phải invalidate cache quyền của **mọi tài khoản bị ảnh hưởng** (tất cả user mang role đó + user đích của ngoại lệ) — đề xuất dùng `CacheService.deleteByPattern`/`invalidateModule` với prefix `seecarauto:v1:rbac:` hoặc xóa từng key user (cơ chế cụ thể do Stage 2 chốt theo RB-04; không quét toàn bộ keyspace bằng `KEYS`). Invalidation chạy **sau khi DB transaction commit** (không nằm trong transaction — Redis không tham gia transaction PostgreSQL); thứ tự commit → invalidate là bắt buộc (xem RB-06).
- **Trường hợp cache lỗi / Redis lỗi / invalidation lỗi (ChatGPT §4 — RB-04, chưa quyết):** brief **không tự chọn** fail-open hay fail-closed cho guard khi Redis lỗi — hai phương án: (a) fallback đọc thẳng DB (đúng kết quả, chậm hơn, vẫn phục vụ request); (b) fail-closed `503 SERVICE_UNAVAILABLE` (theo tiền lệ blacklist M02-05 D-06/AC-18). ADR-006 ghi "fallback khi Redis lỗi" nhưng không ghi rõ fallback là DB hay 503 cho trường hợp quyền. Invalidation lỗi: phương án (a) retry + log/alert, chấp nhận quyền cũ còn hiệu lực tối đa tới hết TTL 300 giây (FR-081 cho phép trễ tới khi invalidate — TTL là chặn trên của độ trễ); (b) fail mutation bằng 503 nếu invalidate không thành công. Cần ChatGPT chốt cả hai.
- **Không dùng cache làm nguồn đúng cho trạng thái thu hồi:** cache chỉ lưu tập quyền đã resolve; trạng thái session/blacklist vẫn do `JwtAuthGuard` kiểm tra trực tiếp (Redis blacklist + DB session) — cache quyền hết hạn/sai không làm token đã logout sống lại.

### 2.6 Audit log — ghi nhận thay đổi role, permission, user-role và user-permission; không ghi token/secret/dữ liệu nhạy cảm

- **Phạm vi audit của M02-06 (FR-084, API_SPEC §18):** mọi thay đổi qua 13 endpoint RBAC (§2.9) đều ghi `AuditLog`: tạo/sửa/xóa role; cập nhật ma trận quyền của role (`PUT /roles/{roleId}/permissions`); gán/bỏ gán role cho tài khoản; cập nhật ngoại lệ quyền theo tài khoản (`PUT /users/{userId}/permissions`). Mỗi row ghi đủ `actorId` (admin thực hiện), `action`, `entityType`, `entityId`, `before`, `after` (JSON — chỉ chứa permission code + cờ `granted` + tên role, **không** token/mật khẩu/hash/SĐT/địa chỉ), `createdAt` (theo schema `AuditLog` đã có — `actorId` bắt buộc + FK tới `User` Restrict, `entityId` nullable UUID).
- **Tên action (đề xuất — chờ ChatGPT chốt ở RB-11):** dùng dạng `<entity>.<verb>` thống nhất, ví dụ `role.created`, `role.updated`, `role.deleted`, `role.permissions_updated`, `user.roles_assigned`, `user.roles_removed`, `user.permissions_updated`. Hiện chưa có catalog tên action nào trong tài liệu — brief không tự chốt catalog cuối; Stage 2 dùng đúng danh sách ChatGPT duyệt.
- **Transaction và audit (ChatGPT §4 — RB-06):** audit insert nằm **trong cùng một PostgreSQL transaction** với thao tác thay đổi quyền (theo tiền lệ M02-05 FIX-08: audit lockout/reuse/revoke-all trong cùng transaction) — thay đổi quyền thất bại/rollback thì **không được để audit ghi nhận một thay đổi chưa commit**; audit insert lỗi → rollback toàn bộ thao tác. Cache invalidation chạy sau commit (xem §2.5), không nằm trong transaction.
- **`GET /audit-logs` (Admin, `audit.view`):** đọc audit theo filter `actorId?`, `entityType?`, `entityId?`, `from?`, `to?` + phân trang (API_SPEC §11.6); response `{ id, actorId, action, entityType, entityId, before, after, createdAt }`. M02-06 chỉ triển khai endpoint đọc audit cho các sự kiện RBAC đã ghi — audit cho thay đổi trạng thái đơn (FR-066) / fitment (FR-033) / sản phẩm thuộc task của các module đó, tái dùng helper ghi audit của M02-06 (xem RB-11).
- **Không ghi audit cho:** login thành công/thất bại thường (theo D-09 của M02-05 — chỉ 4 sự kiện auth được audit); đọc dữ liệu (`GET /roles`, `GET /permissions`, `GET /audit-logs` không tự ghi audit).

### 2.7 Bảo vệ Super Admin cuối cùng — không cho thao tác khiến hệ thống mất tài khoản quản trị cuối cùng

- **Quy tắc (FR-085, BR-007, PRD §6.8, API_SECURITY §2, Error Catalog §3):** mọi thao tác dưới đây, nếu khiến hệ thống không còn tài khoản quản trị nào, đều bị chặn kèm thông báo rõ — **không có ngoại lệ**:
  - (a) `PUT /roles/{roleId}/permissions` bỏ quyền quản trị (`roles.update`/`users.update` hoặc toàn bộ quyền) khỏi role mà tài khoản quản trị cuối cùng đang mang;
  - (b) `DELETE /users/{userId}/roles/{roleId}` bỏ gán role quản trị khỏi tài khoản quản trị cuối cùng;
  - (c) `DELETE /roles/{roleId}` xóa role mà tài khoản quản trị cuối cùng đang mang (và không còn role quản trị nào khác);
  - (d) `PUT /users/{userId}/permissions` đặt ngoại lệ deny (`granted = false`) cho quyền quản trị của tài khoản quản trị cuối cùng;
  - (e) tự sửa quyền của chính mình theo (a)–(d) (PRD §6.8: thay đổi quyền của chính mình yêu cầu xác nhận + ghi audit — xem RB-10; xác nhận không thay thế việc chặn: nếu thao tác vi phạm quy tắc cuối cùng thì vẫn chặn dù đã xác nhận).
- **Mã lỗi (theo Error Catalog §3 + API_SPEC §11.6):** thao tác (a)/(b)/(d)/(e) → `403 LAST_SUPER_ADMIN`; thao tác (c) xóa role → `403 LAST_SUPER_ADMIN_ROLE`. Message tiếng Việt theo Catalog; không lộ thêm thông tin.
- **Định nghĩa "tài khoản quản trị cuối cùng" CHƯA CÓ trong schema — điểm chặn lớn nhất của brief (RB-07, cần ChatGPT phán xét, có thể cần Henry):** schema `User`/`Role` không có cột cờ Super Admin; 5 vai trò ví dụ không được hard-code (ranh giới §3) nên **không được định nghĩa Super Admin bằng tên role "Super Admin"**. Đề xuất các phương án (không tự chọn): (A) tài khoản có đủ tập quyền quản trị tối thiểu (ví dụ: có cả `roles.update` + `users.update` hiệu lực) — định nghĩa bằng quyền, không bằng tên; (B) tài khoản bootstrap do M06-01 tạo được đánh dấu bằng cách riêng (cần thêm cột/marker — thay đổi schema, cần phê duyệt riêng); (C) định nghĩa khác do ChatGPT đưa ra. Mọi thao tác (a)–(e) phải kiểm tra định nghĩa này **trong cùng transaction** với thao tác (đọc số lượng tài khoản quản trị còn lại trước khi commit) để hai request đồng thời không cùng bỏ quyền của hai tài khoản quản trị cuối cùng.
- **Kiểm tra "còn lại bao nhiêu":** đếm tài khoản thỏa định nghĩa quản trị **sau khi** áp dụng thay đổi (mô phỏng trên dữ liệu trong transaction); nếu còn 0 → chặn. Không đếm bằng cache (cache có thể cũ); không đếm bằng token claims.

### 2.8 Seed/catalog dữ liệu quyền — nguồn dữ liệu chuẩn, tính idempotent, cách xử lý permission đã tồn tại

- **Nguồn chuẩn:** API_SPEC §6 (39 code) + OpenAPI `x-required-permission` (đối chiếu §10/§11.2); seed lấy danh sách code từ hai nguồn này — **không lấy từ RBAC Matrix** (matrix là tài liệu UI/UX, có 3 điểm lệch đã ghi ở §10: claim §7 sai với 5 code, gap bảng đã cũ, trích dẫn PRD §6.7 sai).
- **Cơ chế seed (đề xuất — RB-08):** script seed riêng (vd. `backend/prisma/seed-permissions.ts` hoặc lệnh `prisma db seed` — vị trí/cơ chế cuối do Stage 2 chốt theo quyết định RB-08) chạy `upsert` theo unique `(module, action)`: code chưa có → insert (module, action, description từ API_SPEC §6); code đã có → **giữ nguyên, không ghi đè description** (description có thể đã được admin sửa tay); code trong DB mà không có trong catalog chuẩn → **không xóa, chỉ báo cáo** (log danh sách để ChatGPT/M06 xử lý — xóa permission đang được role/user tham chiếu sẽ phá dữ liệu).
- **Tính idempotent:** chạy seed nhiều lần cho kết quả cuối giống hệt nhau (đúng N row, không duplicate — unique `(module, action)` bảo đảm ở DB); seed không tạo role, không gán quyền cho ai, không tạo tài khoản.
- **Hiện trạng đã xác minh:** repo **chưa có file seed nào** (`find *seed*` trong repo không trả kết quả; `backend/prisma/` chỉ có `migrations/` + `schema.prisma`) — seed là file mới hoàn toàn, không sửa seed cũ.
- **Khi seed chạy:** đề xuất chạy một lần khi deploy/migrate M02-06 (cách kích hoạt do Stage 2 chốt theo RB-08); **không** chạy seed trong request path; **không** tự seed khi app boot nếu chưa được duyệt (tránh ghi DB ngoài ý muốn ở môi trường khác).

### 2.9 RBAC management endpoints — 13 operation (API_SPEC §10.8/§11.6)

Các endpoint sau thuộc phạm vi quản trị RBAC; **việc chúng thuộc Stage 2 của M02-06 hay thuộc M06-02/M06-03 là điểm cần ChatGPT chốt (RB-15)** — brief đề xuất triển khai chúng trong M02-06 vì không có chúng thì guard + audit + seed không kiểm thử end-to-end được (không còn cách nào tạo role/gán quyền qua API ngoài ghi trực tiếp DB), còn M06-02/M06-03 xây UI admin trên các endpoint này:

- **Body đã chốt (API_SPEC §11.6):** `POST /roles` `{ name, description }`; `PUT /roles/{roleId}/permissions` `{ permissions: [{ module, action, granted }] }` (thay toàn bộ ma trận của role); `PUT /users/{userId}/permissions` `{ permissions: [{ module, action, granted | null }] }` (`null` = xóa ngoại lệ, dùng quyền của vai trò); `POST /users/{userId}/roles` `{ roleId }`.
- **Validation:** `roleId`/`userId` không tồn tại → `404 ROLE_NOT_FOUND` (Error Catalog §4 — đã có code); `userId` không tồn tại → mã lỗi chưa có trong Catalog (RB-03 — đề xuất `404` với code do ChatGPT chốt, không tự thêm code mới vào Catalog); `module.action` không có trong catalog → RB-03; `name` role trùng → 409 theo quy ước unique (xem RB-03 — Catalog hiện không có code `ROLE_NAME_DUPLICATE`, cần ChatGPT chốt).
- **Không có endpoint `GET /users`, `POST /users`, `GET /users/{userId}`** (đã xác minh trong OpenAPI — chỉ có `/users/{userId}/roles` và `/users/{userId}/permissions`): RBAC chỉ thao tác trên tài khoản đã tồn tại (tạo bởi bootstrap M06-01); không có endpoint liệt kê tài khoản trong P0 — màn hình `/users` là PROVISIONAL (RBAC Matrix §6). Cũng **không có `GET /users/{userId}/roles`** — admin không xem được danh sách role của tài khoản khác qua API (chỉ xem được qua `/me` của chính mình) — ghi nhận là gap cho M06-02 (không tự thêm endpoint).

### 2.10 Rate limit — tái dùng `RateLimitService` (M02-02)

- Mọi endpoint admin đã đăng nhập dùng kind `adminAuthed` sẵn có: **300 lần/phút/tài khoản, fail-open** (theo rule hiện có — `RateLimitService` đã có kind này; API_SPEC §16). Không thêm kind mới cho endpoint RBAC trừ khi ChatGPT quyết khác (RB-12).
- **Giới hạn của fallback bộ nhớ (tiền lệ M02-05 FIX-04):** counter bộ nhớ chỉ dùng chung trong một backend instance — không tuyên bố fallback bảo đảm rate limit toàn hệ thống đa instance.

## 12. Điểm chưa quyết định — cần ChatGPT duyệt trước khi code

**Không tự đặt ra chính sách bảo mật nếu tài liệu chưa quyết định.** Mỗi điểm dưới đây có đề xuất của Muse + lý do + bằng chứng đã kiểm tra; ChatGPT chốt số/phương án cuối cùng. **Trạng thái: TẤT CẢ đều CHƯA QUYẾT ĐỊNH** (Giai đoạn 1 mới soạn xong 28/11/2026, chưa có review nào).

### RB-01 — 4 code `*.view` chỉ dùng cho hiển thị hay còn áp dụng cho API nào?

- Tài liệu: API_SPEC §6 liệt kê `products.view`/`categories.view`/`brands.view`/`articles.view` trong bảng module; OpenAPI không endpoint nào dùng 4 code này (đã xác minh bằng script); RBAC Matrix §2 chú thích 1 ghi "View là quyền hiển thị màn hình, không phải quyền gọi GET" vì các GET tương ứng là public.
- **Đề xuất:** giữ đúng Matrix chú thích 1 — 4 code này **chỉ** dùng cho hiển thị màn hình/sidebar admin (FR-077) + trả về trong `/me` + liệt kê trong `GET /permissions`; guard **không bao giờ** yêu cầu chúng trên bất kỳ endpoint nào (kể cả endpoint admin-only của module — ví dụ `POST /products` yêu cầu `products.create`, không yêu cầu thêm `products.view`). Tài khoản chỉ có `products.view` vẫn gọi được `GET /products` public (200) và bị 403 ở mọi endpoint ghi của module.
- **Cần ChatGPT xác nhận:** đề xuất trên có đúng ý đồ của §6 không, hay §6 muốn 4 code này còn chặn thêm API nào (ví dụ endpoint admin-only lấy danh sách nháp)?

### RB-02 — `fitments.update`: seed vào catalog hay không?

- Mâu thuẫn tài liệu: API_SPEC §6 liệt kê `fitments.view/create/update/delete`; OpenAPI không endpoint nào dùng `fitments.update` (đã xác minh bằng script); RBAC Matrix §2 chú thích 3 ghi module Fitment không có Update (sửa = xóa + gắn lại); RBAC Matrix §6 gap ghi "API_SPEC §6 liệt kê `fitments.update` trong bảng module nhưng không endpoint nào trong OpenAPI dùng code này — ma trận ghi theo OpenAPI".
- **Đề xuất (phương án A — cần ChatGPT chọn):** seed catalog đúng §6 (gồm `fitments.update`) để catalog khớp §6 hoàn toàn; code này tồn tại trong DB + `/me` + `GET /permissions` nhưng không guard nào yêu cầu nó (tương tự 4 code `*.view`). **Phương án B:** không seed `fitments.update` (catalog = 38 code: 34 code endpoint dùng + 4 code `*.view`); `/me` không bao giờ trả code này. Phương án A giữ catalog khớp §6; phương án B giữ catalog khớp hành vi thật của API. Không tự chọn.
- **Hệ quả cần ghi rõ:** nếu chọn A, `PUT /roles/{roleId}/permissions` có thể grant `fitments.update` cho một role mà không endpoint nào kiểm tra — quyền "chết" trong ma trận. Nếu chọn B, `GET /permissions` thiếu một code trong §6 — ma trận checkbox thiếu một ô so với §6.

### RB-03 — Mã lỗi cho userId không tồn tại / permission code không tồn tại / tên role trùng

- Tài liệu: Error Catalog §4 chỉ có `ROLE_NOT_FOUND` (404) trong nhóm RBAC; **không có `USER_NOT_FOUND` / `PERMISSION_NOT_FOUND`**; không có code 409 cho tên role trùng (role `name` unique ở DB).
- **Đề xuất:** (a) `userId` không tồn tại ở `POST/DELETE /users/{userId}/roles` và `GET/PUT /users/{userId}/permissions` → `404` với code mới `USER_NOT_FOUND` (thêm vào Catalog — cần ChatGPT duyệt tên code + message); (b) `module.action` không có trong catalog ở body PUT → `400 VALIDATION_ERROR` với `details: [{ field: "permissions[i].action", code: "UNKNOWN_PERMISSION" }]` (không thêm code 404 mới — coi là lỗi validation, không phải resource không tồn tại); (c) tên role trùng khi `POST /roles` / `PATCH /roles/{roleId}` → `409` với code mới `ROLE_NAME_DUPLICATE` (hoặc dùng code 409 chung đã có trong Catalog nếu ChatGPT chỉ ra — cần kiểm tra Catalog §5 trước khi chốt).
- **Cần ChatGPT chốt:** tên code + status cho từng trường hợp (a)/(b)/(c); có cập nhật Error Catalog trong Giai đoạn 2 không (sửa Catalog là sửa tài liệu đã nghiệm thu — cần ghi rõ trong báo cáo Stage 2).

### RB-04 — Trường hợp permission không tồn tại, cache lỗi, Redis lỗi và invalidation lỗi

- Tài liệu: ADR-006 ghi "fallback khi Redis lỗi" nhưng không ghi rõ fallback là gì cho trường hợp quyền; M02-05 D-06/AC-18 đặt tiền lệ fail-closed 503 cho blacklist (token đã thu hồi không được sống lại khi Redis lỗi); FR-081 cho phép quyền mới có hiệu lực "sau khi cache invalidate" (TTL 300 giây là chặn trên độ trễ).
- **Đề xuất:** (a) Guard đọc cache lỗi / Redis lỗi khi kiểm tra quyền → **fallback đọc thẳng DB** (fail-open về DB: kết quả đúng, chậm hơn, vẫn phục vụ request; khác với blacklist — sai sót ở đây chỉ làm chậm, không làm token đã thu hồi sống lại vì blacklist/session vẫn do JwtAuthGuard kiểm tra riêng). **Phương án thay thế:** fail-closed `503 SERVICE_UNAVAILABLE` như blacklist. (b) Invalidation lỗi sau khi DB đã commit → **retry tối đa 3 lần + log/alert, không fail mutation** (quyền cũ còn hiệu lực tối đa tới hết TTL 300 giây — trong giới hạn FR-081); **phương án thay thế:** fail mutation bằng 503 nếu invalidate không thành công (DB đã commit nhưng client nhận lỗi — cần cơ chế bù trừ, phức tạp hơn).
- **Cần ChatGPT chốt:** chọn (a) hay phương án thay thế cho cả hai trường hợp; ghi rõ vào AC-06 khi Stage 2 bắt đầu.

### RB-05 — Thứ tự ưu tiên giữa role grant và user-level deny

- Tài liệu: API_SECURITY §2 ghi "ngoại lệ `granted=false` có thể thu hồi quyền của vai trò cho tài khoản đó — M02 chốt semantics cuối: deny lấn át allow"; `AuthService.getMe()` (đã nghiệm thu G4) triển khai deny thắng allow cho **mọi** nguồn deny (cấp role và cấp user gộp chung một tập denies).
- **Đề xuất:** xác nhận semantics cuối đúng như `getMe` đã làm: bất kỳ `granted = false` nào (ở `role_permissions` của bất kỳ role nào tài khoản mang, hay ở `user_permissions`) cũng loại code khỏi tập quyền cuối — kể cả trường hợp role A grant + role B deny cùng code, và trường hợp user-level grant + role-level deny cùng code (deny thắng, user không tự grant lại được quyền mà role đã deny).
- **Cần ChatGPT xác nhận tường minh** từng cặp xung đột (role grant vs role deny; role grant vs user deny; user grant vs role deny; user grant vs user deny — trường hợp cuối không xảy ra vì `(userId, permissionId)` là PK duy nhất) vì API_SECURITY §2 chưa liệt kê hết các cặp; nếu ChatGPT muốn semantics khác (ví dụ user-level grant thắng role-level deny) thì `getMe` phải sửa theo — đó là thay đổi hành vi đã nghiệm thu, cần ghi rõ.

### RB-06 — Transaction và audit log: thay đổi quyền thất bại thì không được để audit ghi nhận thay đổi chưa commit

- Tài liệu: M02-05 FIX-08 đặt tiền lệ audit lockout/reuse/revoke-all trong cùng transaction; API_SPEC §18 yêu cầu audit đủ fields; RBAC Matrix §5 yêu cầu ghi đủ trước–sau.
- **Đề xuất:** mọi mutation quyền (PUT role permissions, PUT user permissions, gán/bỏ gán role, tạo/sửa/xóa role) chạy trong **một Prisma transaction duy nhất**: thay đổi dữ liệu quyền + insert AuditLog; commit cùng nhau hoặc rollback cùng nhau. **Cache invalidation chạy sau khi transaction commit** (Redis không tham gia transaction PostgreSQL) — thứ tự bắt buộc: commit DB → invalidate cache; nếu invalidate lỗi thì xử lý theo RB-04 (không rollback DB đã commit).
- **Cần ChatGPT xác nhận:** quy tắc "audit lỗi → rollback thay đổi" có áp dụng cho mọi mutation quyền không (kể cả trường hợp audit insert lỗi do DB, không phải do dữ liệu sai); và trường hợp process chết giữa commit DB và invalidate (quyền mới trong DB nhưng cache cũ còn tới 300 giây) có chấp nhận được không (FR-081 cho phép trễ tới khi invalidate).

### RB-07 — Quy tắc Super Admin cuối cùng trong các thao tác tự sửa quyền, gỡ role và xóa role

- Tài liệu: FR-085/BR-007/PRD §6.8/API_SECURITY §2/Error Catalog §3 + API_SPEC §11.6 đều yêu cầu chặn; nhưng **schema không có cột cờ Super Admin** và 5 vai trò ví dụ không được hard-code (ranh giới §3) — định nghĩa "tài khoản quản trị" chưa có dạng triển khai được.
- **Đề xuất (phương án A — cần ChatGPT chọn):** định nghĩa bằng quyền, không bằng tên: tài khoản được coi là "quản trị" nếu tập quyền hiệu lực của nó chứa đủ quyền quản trị tối thiểu — đề xuất tối thiểu là **cả `roles.update` và `users.update`** (hai quyền cho phép thay đổi phân quyền). Mọi thao tác §2.7 (a)–(e) đếm số tài khoản thỏa định nghĩa này **sau khi** áp dụng thay đổi, trong cùng transaction; nếu còn 0 → chặn. **Phương án B:** M06-01 đánh dấu tài khoản bootstrap bằng marker riêng (cần thêm cột/marker vào schema — thay đổi schema, cần phê duyệt riêng và migration mới, không thuộc M02-06 nếu chưa duyệt). **Phương án C:** định nghĩa khác do ChatGPT đưa ra.
- **Cần ChatGPT chốt (có thể cần Henry vì chạm định nghĩa nghiệp vụ):** chọn phương án; nếu chọn A thì chốt tập quyền tối thiểu (chỉ `roles.update` + `users.update`, hay toàn bộ quyền roles/users, hay thêm `audit.view`?); xác nhận mapping mã lỗi: xóa role → `LAST_SUPER_ADMIN_ROLE`, các thao tác còn lại → `LAST_SUPER_ADMIN` (theo API_SPEC §11.6 + Catalog §3).

### RB-08 — Seed/catalog dữ liệu quyền: nguồn, cơ chế, thời điểm chạy

- Tài liệu: nguồn chuẩn là API_SPEC §6 + OpenAPI (đã đối chiếu §10); repo chưa có cơ chế seed nào; RBAC Matrix §7 nhắc "kiểm tra bằng script đối chiếu (Task Brief M01-05 §9.6)" cho ma trận — script đó kiểm tra ma trận, không phải seed.
- **Đề xuất:** seed là script riêng `backend/prisma/seed-permissions.ts` (chạy bằng `prisma db seed` hoặc `pnpm exec tsx` — cơ chế cuối do Stage 2 chốt), dùng `upsert` theo unique `(module, action)`; chạy một lần khi deploy/migrate M02-06 (không chạy trong request path, không tự chạy khi app boot nếu chưa duyệt). Code đã có trong DB mà ngoài catalog → không xóa, chỉ log báo cáo. Description của code đã có → không ghi đè.
- **Cần ChatGPT chốt:** vị trí file + lệnh chạy seed; seed chạy tự động ở bước nào (migrate deploy? CI? deploy tay?); có cho phép seed chạy lại ở production không; description mặc định của mỗi code lấy từ đâu (API_SPEC §6 không có description từng code — đề xuất description = chính code, hoặc để null).

### RB-09 — Cơ chế guard/decorator: guard + decorator hay middleware?

- Tài liệu: API_SPEC §6 ghi "middleware/guard kiểm tra permission code trước khi vào handler"; API_SECURITY §2 ghi "Guard kiểm tra permission code trước handler"; M02-05 đã dùng `JwtAuthGuard` (CanActivate) — tiền lệ trong repo là guard, không phải middleware Express.
- **Đề xuất:** theo tiền lệ M02-05 — dùng NestJS guard (`PermissionsGuard` implements `CanActivate`) + decorator `@RequirePermission(code)`; không dùng middleware Express (middleware không đọc được metadata của handler). Guard chạy sau `JwtAuthGuard` trong cùng chuỗi guard (thứ tự §2.3). Không cần `@RequireAnyPermission` (mọi operation chỉ có một code) — nếu Stage 2 phát hiện operation cần nhiều code thì xin quyết định riêng, không tự thêm decorator.
- **Cần ChatGPT xác nhận:** chọn guard + decorator (đề xuất trên) hay middleware; thứ tự guard trong chuỗi; guard áp dụng global (đọc metadata, bỏ qua khi không có metadata) hay gắn từng controller (đề xuất gắn từng controller admin để không chặn nhầm endpoint public — cần chốt).

### RB-10 — Tự sửa quyền của chính mình: xác nhận ở backend hay chỉ UI?

- Tài liệu: PRD §6.8 — "thay đổi quyền của chính mình → yêu cầu xác nhận và ghi audit log" (xác nhận là bước trong luồng UI); RBAC Matrix §5 ghi cùng quy tắc (trích dẫn sai §6.7 — xem §10 G-1).
- **Đề xuất (phương án A — cần ChatGPT chọn):** xác nhận là **trách nhiệm của frontend** (dialog xác nhận trước khi gọi API) + backend **ghi audit** mọi lần tự sửa quyền (actorId = target userId → nhận diện được trong audit); backend không yêu cầu thêm field xác nhận. **Phương án B:** backend bắt buộc body có `confirm: true` khi actor tự sửa quyền của chính mình (thiếu → `400 VALIDATION_ERROR`); frontend gửi kèm flag sau khi user xác nhận. Phương án B bắt buộc sửa contract API (thêm field) — cần ChatGPT duyệt vì chạm API_SPEC §11.6.
- **Cần ChatGPT chốt:** chọn A hay B; nếu chọn B thì chốt tên field + mã lỗi; lưu ý: xác nhận không thay thế việc chặn Super Admin cuối cùng (RB-07) — đã xác nhận mà vẫn vi phạm thì vẫn 403.

### RB-11 — Tên action audit + phạm vi audit của M02-06

- Tài liệu: API_SPEC §18 liệt kê fields audit nhưng không có catalog tên action; FR-084 yêu cầu ghi đủ ai/khi nào/vai trò nào/quyền nào đổi (trước–sau); API_SPEC §18 ghi "M02 mở rộng audit cho các thao tác này" (tạo/sửa/xóa sản phẩm/danh mục/thương hiệu/xe) — nhưng đó là audit cho các module khác, không phải M02-06.
- **Đề xuất:** catalog tên action dạng `<entity>.<verb>` cho 7 sự kiện RBAC: `role.created`, `role.updated`, `role.deleted`, `role.permissions_updated`, `user.roles_assigned`, `user.roles_removed`, `user.permissions_updated` (§2.6). M02-06 cung cấp helper ghi audit + ghi audit cho các thay đổi RBAC; **audit cho thay đổi sản phẩm/đơn/fitment thuộc task của từng module** (M03/M04/M05) tái dùng helper — M02-06 không tự ghi audit cho các module chưa tồn tại.
- **Cần ChatGPT chốt:** catalog tên action (đúng 7 tên trên hay khác); phạm vi helper (chỉ RBAC hay dùng chung ngay từ đầu); `entityType` dùng giá trị nào (`ROLE`/`USER`/`PERMISSION` — API_SPEC §11.6 ví dụ `ROLE` | `ORDER` | `FITMENT` | `PRODUCT` ... — chưa chốt giá trị cho RBAC).

### RB-12 — Rate limit cho endpoint RBAC: giữ `adminAuthed` hay thêm kind riêng?

- Tài liệu: API_SPEC §16 — admin đã đăng nhập 300 lần/phút/tài khoản (`adminAuthed`, fail-open); không có limit riêng cho endpoint RBAC; M02-02 đã có kind này sẵn.
- **Đề xuất:** giữ `adminAuthed` cho mọi endpoint RBAC (không thêm kind mới) — các endpoint này chỉ admin đã đăng nhập mới gọi được, tần suất thấp, không phải credential như login/refresh nên không cần fail-closed riêng.
- **Cần ChatGPT xác nhận:** giữ nguyên (đề xuất trên) hay muốn limit riêng cho mutation RBAC (ví dụ fail-closed vì đổi quyền là thao tác nhạy cảm)?

### RB-13 — Vị trí hàm resolve permission dùng chung (M02-05 D-10)

- Tài liệu: M02-05 D-10 — `/me` resolve trực tiếp từ DB qua "một hàm dùng chung (`permission.service` hoặc hàm trong `auth.service`) mà middleware M02-06 sẽ tái dùng"; hiện tại logic nằm trong `AuthService.getMe()` (`backend/src/auth/auth.service.ts`), chưa tách ra.
- **Đề xuất:** tách thành `PermissionService` mới trong `RbacModule` (`backend/src/rbac/permission.service.ts`); `AuthService.getMe()` gọi lại `PermissionService` (giữ nguyên response — AC-13); `PermissionsGuard` dùng cùng service. Không giữ hai bản copy của logic resolve.
- **Cần ChatGPT xác nhận:** tách ra service riêng (đề xuất trên) hay giữ logic trong `AuthService` và export hàm cho `RbacModule` dùng (tránh tạo module mới chỉ cho một hàm); nếu tách thì `AuthModule` import `RbacModule` hay `RbacModule` import `AuthModule` (tránh circular dependency — `RbacModule` cần `JwtAuthGuard` từ `AuthModule`, `AuthService` cần `PermissionService` từ `RbacModule`).
